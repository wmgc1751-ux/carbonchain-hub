# 碳链通 CarbonChain Hub

> 企业碳足迹存证与碳配额交易平台 —— 基于区块链的碳排放数据可信治理与碳资产流转系统

## 一、选题背景

全国碳排放权交易市场已覆盖发电、钢铁、建材、化工等八大高排放行业，年覆盖二氧化碳排放量超过 50 亿吨。这个市场的地基是**数据**：企业申报的排放量决定配额缺口，配额缺口决定真金白银的交易与履约。

而碳排放数据的天然痛点是：**由被监管者自己申报，且极易被修改**。

- 企业端：改一个数，就能少买几百万元的配额；
- 核查机构端：报告签发后仍可被"二次编辑"，责任无法界定；
- 监管端：拿到的是二手的 Excel，无法证明数据未被中间环节调整；
- 公众端：碳市场的运行数据几乎是黑箱，"谁排了多少、谁买了多少"无从核验。

本项目把**区块链**用在它真正不可替代的地方 —— 不是发币，而是**给碳数据提供一个防篡改、可追溯、可第三方独立验证的可信层**：

| 业务动作 | 链上动作 | 解决的问题 |
| --- | --- | --- |
| 企业上报季度排放数据 | 企业私钥签名 → 上链存证 | 数据来源不可抵赖 |
| 核查机构出具核查报告 | 机构私钥签名 + 报告签章摘要上链 | 报告签发后不可篡改 |
| 监管端下发年度配额 | 监管节点签名 → 上链存证 | 配额分配全程留痕 |
| 碳配额撮合成交 | 成交即存证，链上时间戳为清算时点 | 账实相符、可审计 |

### 技术选型说明

| 层次 | 选型 | 理由 |
| --- | --- | --- |
| 后端 | Node.js 22 + Express 4 | 与前端同语言，便于统一口径；Node 内置 `crypto` 足以实现完整密码学原语，**不引入任何区块链第三方库**，所有链逻辑自研，便于答辩讲清原理 |
| 数据库 | MySQL 8.0 | 课程环境已具备；链上链下同库不同表，便于演示"改库 vs 改链"的对照 |
| 前端 | Vue 3.4 + ECharts 5.5 | 前端依赖本地化（`public/vendor/`），**无构建步骤**，`git clone` 后即可运行，部署零障碍 |

| 区块链 | 自研联盟链内核 | SHA-256 哈希链 + 工作量证明 + Merkle 树 + secp256k1 ECDSA 签名 |

## 三、功能模块（四个端）

### 1. 企业端（控排企业）
- **企业总览**：年度累计排放、配额余额、履约缺口、行业排名、链上钱包身份
- **碳排放上报**：在线填报能源消耗明细（7 类能源品种），系统自动折算范围一/范围二排放，提交即上链存证并自动派单核查
- **碳配额账户**：年度配额、可用/冻结/已用/买卖明细、监管端分配流水的链上溯源
- **碳配额交易**：市场买卖盘、下单、撤单、成交记录，成交即上链
- **数据分析**：排放趋势、能源结构、同行对标、交易行为
- **链上身份**：钱包地址、公钥、由本钱包签发的全部存证交易

### 2. 核查机构端（第三方核查机构）
- **机构总览**：待受理/核查中/已完成任务、平均偏差率、链上存证笔数
- **核查作业台**：企业档案、历史排放序列、同期行业均值对标、申报明细逐行核验
- **出具核查报告**：录入认定值与结论 → 系统计算电子签章摘要 → 机构私钥签名 → 上链存证
- **核查报告台账**：历次报告，支持链上存证核验

### 3. 监管端（生态环境主管部门）
- **监管驾驶舱**：8 项核心指标 + 排放趋势 + 核查进度 + 碳价走势 + 行业/区域结构 + 履约风险 TOP10
- **控排企业名录**：多条件筛选、企业全景档案（上报/配额/成交/预警/存证五维）
- **配额分配管理**：下发年度配额（历史强度法 / 行业基准线法 / 历史总量法 / 有偿竞价），分配即上链
- **碳市场交易监管**：全市场成交穿透式查询、价格异动自动检测（±2σ）
- **预警与风险处置**：五类预警（配额超限/数据异常/漏报/价格异动/链上风险）的分级处置与闭环
- **统计分析**：行业、区域、规模、能源结构、减排成效、履约合规六维分析
- **操作审计日志**：全平台操作行为留痕（等保安全审计要求）
- **系统与链自检**：数据规模统计 + 全链完整性校验 + 篡改实验

### 4. 公众端（无需登录）
- **数据公示大屏**：全市场行情、排放结构、实时出块、政策公告
- **区块链浏览器**：区块列表/详情、交易列表/详情、Merkle 存在性证明、ECDSA 验签、**防篡改实验台**

## 四、区块链设计（本项目的技术核心）

### 4.1 区块结构

```
区块头 header（参与哈希计算）
├── index         区块高度
├── timestamp     出块时间戳（秒级，与 DATETIME 精度对齐）
├── merkleRoot    区块内所有交易 ID 构建的 Merkle 根
├── prevHash      前一区块哈希（形成链式引用）
├── difficulty    难度（要求哈希前导零个数）
└── nonce         工作量证明随机数

blockHash = SHA256(index | timestamp | merkleRoot | prevHash | difficulty | nonce)
```

### 4.2 工作量证明（PoW）

`proofOfWork()` 暴力搜索 `nonce`，直到区块哈希以 `difficulty` 个 `0` 开头。当前难度为 **4**（平均需尝试 65,536 次），实测平均出块耗时约 60–80 ms，既能让答辩现场"看得见计算过程"，又不至于卡顿。

### 4.3 交易与数字签名

```
txId        = SHA256(from | nonce | payloadHash | txType | bizNo)
payloadHash = SHA256(stableStringify(业务数据))
signature   = ECDSA-secp256k1-SHA256(交易核心字段, 发起方私钥)
```

- **为什么先做 `stableStringify`**：JSON 的键顺序不稳定，`{a:1,b:2}` 与 `{b:2,a:1}` 必须得到同一摘要，否则多节点共识会崩。本项目对对象键做字典序排序后再序列化。
- **签名覆盖范围**：交易号、类型、业务单号、收发地址、数据摘要、nonce —— 任何一个字段被改，验签立刻失败。

### 4.4 钱包与密钥托管

| 数据 | 存放位置 | 谁能看到 |
| --- | --- | --- |
| 钱包地址、公钥 | MySQL 业务表 `enterprise.wallet_address` / `verifier_org.pub_key` | 公开 |
| 私钥（PEM） | 节点本地 `server/keystore.json` | 仅节点 |

业务库中不含任何私钥 —— 即使数据库被脱库，攻击者也无法伪造任何主体的存证签名。生产中该密钥库应替换为 HSM 或云 KMS；作业中以本地密钥库等价实现。

### 4.5 全链完整性校验（四道关）

`GET /api/chain/validate` 会逐块执行：

1. **重算哈希** —— 用区块头字段重新计算 SHA-256，与记录的 `block_hash` 比对；
2. **PoW 难度** —— 校验哈希确实满足 `difficulty` 个前导零；
3. **前向引用** —— 校验 `prev_hash` 确实指向上一区块（链是否断裂）；
4. **Merkle 根** —— 由链上交易表重新构建 Merkle 树，与区块头记录比对（交易是否被增删改）。

### 4.6 防篡改实验台（答辩演示重点）

浏览器页面提供一键实验：

| 操作 | 结果 |
| --- | --- |
| 直接改写某区块的 `merkle_root`（模拟恶意节点绕过应用层改库） | 全链校验立刻失败：`HASH_MISMATCH` + `MERKLE_ROOT_MISMATCH` |
| 改写 `prev_hash` | 除本块哈希失配外，下一块的链式引用断裂 |
| 改写 `nonce` | 本块哈希失配 + `POW_INVALID`（不再满足难度） |
| 改写 `block_time` | 时间戳参与哈希，同样立即暴露 |
| 点击"重做工作量证明并修复" | 系统从被改区块起重算整条后缀的哈希并重做 PoW —— 实测 147 个区块耗时约 11 秒，且**所有后续区块哈希全部改变**，任何持有旧链的节点都能立刻发现分叉 |

> 这一实验直观说明了工作量证明的经济学威慑：篡改不是"改一个数"，而是"重做整条链的计算"，且必然留下全网可见的痕迹。

## 七、快速开始

### 7.1 环境要求

| 组件 | 版本 | 说明 |
| --- | --- | --- |
| Node.js | ≥ 18（推荐 20/22） | 需支持 `crypto.createSign` 与 `globalThis.fetch` |
| MySQL | 8.0 | 需已启动，默认连接 `127.0.0.1:3306` |

### 7.2 三步启动

```bash
# 1. 安装依赖（仅 express / mysql2 / vue / echarts 四个）
npm install

# 2. 初始化数据库：建库建表 + 生成 16 张表仿真数据 + 真实构建区块链
npm run initdb

# 3. 启动服务
npm start
```

Windows 用户可直接双击 `init-db.bat` 与 `start.bat`（已内置 `chcp 65001`，避免中文乱码）。

启动后访问：**http://localhost:8300**

若数据库口令不是 `123456`，请在启动前设置环境变量：

```bash
set DB_PASSWORD=你的密码
```

## 九、关键设计取舍与不足

**取舍：为什么区块链与业务库放在同一个 MySQL 实例？**
本作业是单机演示环境，同库便于对照"改库 vs 改链"。真实联盟链部署中，链上数据应由各参与方各自持有全量副本，通过 P2P 与共识算法同步 —— 这样即使某一方的数据库被完全攻陷，也无法改变其他节点上的链。

**不足与后续改进方向：**
1. 当前为单节点出块，"最长链原则"下的分叉重组未实现（需要一个多节点 P2P 网络层）；
2. 撮合引擎未做压力测试与内存订单簿优化，高频场景下应引入撮合队列；
3. 企业排放数据的采集仍以人工填报为主，可对接在线监测设备（CEMS）自动采数并直接上链；
4. 隐私保护方面，当前所有业务数据以明文快照上链，真实场景应改为"链上存哈希 + 链下加密存储"或引入零知识证明。

## 十、常见问题

**Q：启动报 `Unknown database 'carbon_chain'`？**
先执行 `npm run initdb`。

**Q：中文在命令行里显示为乱码？**
Windows 控制台默认代码页为 GBK。使用 `start.bat`（已内置 `chcp 65001`），或先执行 `chcp 65001`。

**Q：初始化时间较长？**
正常现象。`npm run initdb` 会真实执行 900+ 次 ECDSA 签名与 155 次工作量证明出块，实测约 16 秒。

**Q：端口 8300 被占用？**
`set PORT=8400` 后重新启动。

**Q：想清空重来？**
`npm run initdb` 会 `DROP DATABASE` 后完整重建，可反复执行。
