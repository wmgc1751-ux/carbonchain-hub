# 碳链通 CarbonChain Hub

> 面向工业场景的联盟链碳资产动态核算可信存证平台 —— 基于联盟链（PoA）的碳排放数据可信治理、动态核算与碳配额交易系统

## 一、选题背景

全国碳排放权交易市场已覆盖发电、钢铁、建材、化工等八大高排放行业，年覆盖二氧化碳排放量超过 50 亿吨。这个市场的地基是**数据**：企业申报的排放量决定配额缺口，配额缺口决定真金白银的交易与履约。

而碳排放数据的天然痛点是：**由被监管者自己申报，且极易被修改**。

- 企业端：改一个数，就能少买几百万元的配额；
- 核查机构端：报告签发后仍可被"二次编辑"，责任无法界定；
- 监管端：拿到的是二手的 Excel，无法证明数据未被中间环节调整；
- 公众端：碳市场的运行数据几乎是黑箱，"谁排了多少、谁买了多少"无从核验。

本项目把**区块链**用在它真正不可替代的地方 —— 不是发币，而是**给碳数据提供一个防篡改、可追溯、可第三方独立验证的可信层**：

| 业务动作 | 链上动作 | 解决的问题 |
| --- | --- | --- |
| 企业上报季度排放数据 | 企业私钥签名 → 上链存证 | 数据来源不可抵赖 |
| 核查机构出具核查报告 | 机构私钥签名 + 报告签章摘要上链 | 报告签发后不可篡改 |
| 监管端下发年度配额 | 监管节点签名 → 上链存证 | 配额分配全程留痕 |
| 碳配额撮合成交 | 成交即存证，链上时间戳为清算时点 | 账实相符、可审计 |

## 三、功能模块（四个端）

### 1. 企业端（控排企业）
- **企业总览**：年度累计排放、配额余额、履约缺口、行业排名、链上钱包身份
- **碳排放上报**：在线填报能源消耗明细（7 类能源品种），系统自动折算范围一/范围二排放，提交即上链存证并自动派单核查
- **碳资产动态核算**：对接工业排口 CEMS 在线监测的准实时读数，按企业配额规模滚动核算累计排放、预测期末排放与配额缺口，实时给出履约风险等级（区别于传统的季度人工填报）
- **碳配额账户**：年度配额、可用/冻结/已用/买卖明细、监管端分配流水的链上溯源
- **碳配额交易**：市场买卖盘、下单、撤单、成交记录，成交即上链
- **数据分析**：排放趋势、能源结构、同行对标、交易行为
- **链上身份**：钱包地址、公钥、由本钱包签发的全部存证交易

### 2. 核查机构端（第三方核查机构）
- **机构总览**：待受理/核查中/已完成任务、平均偏差率、链上存证笔数
- **核查作业台**：企业档案、历史排放序列、同期行业均值对标、申报明细逐行核验
- **出具核查报告**：录入认定值与结论 → 系统计算电子签章摘要 → 机构私钥签名 → 上链存证
- **核查报告台账**：历次报告，支持链上存证核验

### 3. 监管端（生态环境主管部门）
- **监管驾驶舱**：8 项核心指标 + 排放趋势 + 核查进度 + 碳价走势 + 行业/区域结构 + 履约风险 TOP10
- **控排企业名录**：多条件筛选、企业全景档案（上报/配额/成交/预警/存证五维）
- **配额分配管理**：下发年度配额（历史强度法 / 行业基准线法 / 历史总量法 / 有偿竞价），分配即上链
- **碳市场交易监管**：全市场成交穿透式查询、价格异动自动检测（±2σ）
- **动态核算监管**：辖区企业 CEMS 实测排放总览、滚动核算账户、配额缺口与履约风险分布，缺口越限自动生成预警
- **联盟链治理**：联盟成员节点准入审批、出块权授予/吊销、各节点链副本一致性核验与一键同步
- **预警与风险处置**：五类预警（配额超限/数据异常/漏报/价格异动/链上风险）的分级处置与闭环
- **统计分析**：行业、区域、规模、能源结构、减排成效、履约合规六维分析
- **操作审计日志**：全平台操作行为留痕（等保安全审计要求）
- **系统与链自检**：数据规模统计 + 全链完整性校验 + 篡改实验

### 4. 公众端（无需登录）
- **数据公示大屏**：全市场行情、排放结构、实时出块、政策公告
- **区块链浏览器**：区块列表/详情、交易列表/详情、Merkle 存在性证明、ECDSA 验签、**防篡改实验台**

## 四、区块链设计（本项目的技术核心）

### 4.1 区块结构

```
区块头 header（参与哈希计算）
├── index         区块高度
├── timestamp     出块时间戳（秒级，与 DATETIME 精度对齐）
├── merkleRoot    区块内所有交易 ID 构建的 Merkle 根
├── prevHash      前一区块哈希（形成链式引用）
├── consensus     共识标识（POA / POW，用于向后兼容历史区块）
├── proposer      本块出块节点（联盟授权成员 ID，PoA）
└── nonce         随机数（PoW 下为工作量证明随机数；PoA 下为节点出块序号）

blockHash(PoA) = SHA256(index | timestamp | merkleRoot | prevHash | "POA" | proposer | nonce)
blockHash(PoW) = SHA256(index | timestamp | merkleRoot | prevHash | difficulty | nonce)   ← 历史区块沿用
```

> 哈希算法按区块的 `consensus` 字段分派，因此**旧 PoW 区块与新区块可以在同一条链上被正确校验**，实现共识平滑升级。

### 4.2 共识机制：权威证明 PoA（联盟链范式）

本项目定位为**联盟链**，采用 **PoA（Proof of Authority，权威证明）** 出块，而非公有链的挖矿：

| 维度 | 传统 PoW（公有链） | 本项目 PoA（联盟链） |
| --- | --- | --- |
| 出块权 | 算力竞争，谁都能参与 | **仅授予联盟授权成员节点**（准入白名单） |
| 出块顺序 | 先算出来者胜 | 按成员**投票权重的轮值序列**依次出块 |
| 出块方式 | 暴力搜索 nonce（耗时、耗电） | 直接打包 + **ECDSA 签名**，毫秒级出块 |
| 防篡改依据 | 重做算力的经济成本 | **区块链式引用 + 出块签名**：改一块则后缀哈希全变、签名失效，各成员节点拒收 |
| 成员准入 | 无许可（Permissionless） | 许可制（Permissioned）：申请 → 监管审批 → 授予出块权 |

- 创世初始化登记 **5 个联盟成员节点**（省级监管部门权重 3、核查机构 2 与 1、控排企业 1、审计机构 1），出块按权重展开的轮值序列进行；
- 出块节点用**由确定性密钥派生的钱包私钥**对区块头签名，`validateChain` 会逐块验签并核对出块者是否为授权节点；
- 私钥由 `keystore` 托管、加密落盘；节点出块权的**授予与吊销**由监管端在线操作（见 [4.7](#47-联盟链成员治理与链副本同步)）。

### 4.3 交易与数字签名

```
txId        = SHA256(from | nonce | payloadHash | txType | bizNo)
payloadHash = SHA256(stableStringify(业务数据))
signature   = ECDSA-secp256k1-SHA256(交易核心字段, 发起方私钥)
```

- **为什么先做 `stableStringify`**：JSON 的键顺序不稳定，`{a:1,b:2}` 与 `{b:2,a:1}` 必须得到同一摘要，否则多节点共识会崩。本项目对对象键做字典序排序后再序列化。
- **签名覆盖范围**：交易号、类型、业务单号、收发地址、数据摘要、nonce —— 任何一个字段被改，验签立刻失败。

### 4.4 钱包与密钥托管

| 数据 | 存放位置 | 谁能看到 |
| --- | --- | --- |
| 钱包地址、公钥 | MySQL 业务表 `enterprise.wallet_address` / `verifier_org.pub_key` | 公开 |
| 私钥（PEM） | 节点本地 `server/keystore.json`（**AES-256-GCM 加密落盘**，密钥由 `KEYSTORE_SECRET` 环境变量注入） | 仅节点 |

业务库中不含任何私钥；密钥库文件即使泄露，无 `KEYSTORE_SECRET` 也无法还原私钥。生产中该密钥库应替换为 HSM 或云 KMS；作业中以本地加密密钥库等价实现。

### 4.5 全链完整性校验（五道关）

`GET /api/chain/validate` 会逐块执行：

1. **重算哈希** —— 用区块头字段重新计算 SHA-256，与记录的 `block_hash` 比对；
2. **共识规则** —— PoW 块校验前导零难度；**PoA 块校验出块签名**（`proposer_sig` 是否由 `proposer` 的节点公钥签出）；
3. **出块权** —— PoA 块校验其 `proposer` 是否为**当前授权节点**（出块权被吊销的节点所出区块将被判为非法）；
4. **前向引用** —— 校验 `prev_hash` 确实指向上一区块（链是否断裂）；
5. **Merkle 根** —— 由链上交易表重新构建 Merkle 树，与区块头记录比对（交易是否被增删改）。

### 4.6 防篡改实验台（答辩演示重点）

浏览器页面提供一键实验：

| 操作 | 结果 |
| --- | --- |
| 直接改写某区块的 `merkle_root`（模拟恶意节点绕过应用层改库） | 全链校验立刻失败：`HASH_MISMATCH` + `MERKLE_ROOT_MISMATCH` |
| 改写 `prev_hash` | 除本块哈希失配外，下一块的链式引用断裂 |
| 改写 `proposer_sig` / 伪造出块者 | **`POA_SIGNATURE_INVALID`** 或 **`PROPOSER_UNAUTHORIZED`**（PoA 新增校验） |
| 改写 `block_time` | 时间戳参与哈希，同样立即暴露 |
| 点击"按共识重新出块并修复" | 系统从被改区块起按共识重新出块（PoA 下为重新签名，秒级完成）——**所有后续区块哈希全部改变**，任何持有旧链的成员节点都能立刻发现分叉 |

> 实验直观说明了联盟链的防篡改逻辑：篡改不是"改一个数"，而是要让**整条后缀重新出块并对齐所有成员节点的签名**，任何一处不一致都会被全链校验和成员节点同步检查立刻察觉。

### 4.7 联盟链成员治理与链副本同步

这是让"联盟链"名副其实的核心模块（`server/services/consortium.js` + `chain_node` / `chain_node_replica` 两张表）：

| 能力 | 说明 |
| --- | --- |
| **成员准入** | 新节点提交入盟申请（`POST /api/consortium/nodes/apply`）→ 监管端审批（`approve`）→ 进入白名单 |
| **出块权管理** | 授予 / 吊销出块权（`revoke`），被吊销的节点产物不被链校验接受 |
| **按权重轮值出块** | 出块顺序由成员 `vote_weight` 展开的确定性轮值序列决定，实测各节点出块数与其权重成正比 |
| **多方各自持链** | 每个成员节点维护一份链副本（`chain_node_replica`），节点可 `sync` / `desync` |
| **副本一致性核验** | `GET /api/consortium/replica` 汇总主链高度、各节点副本高度与落后量、一致节点数 |

> 这一设计直接回应了"链上链下同库 = 攻陷数据库即攻陷链"的质疑：链由多方各自持副本，单方篡改其本地库无法改变其他节点的链。

### 4.8 碳资产动态核算引擎

这是让"动态核算"名副其实的核心模块（`server/services/dynamic.js` + `cems_reading` / `carbon_dynamic_account` 两张表），把核算从"季度人工填报"升级为"准实时滚动"：

```
工业排口 CEMS 在线监测  ──每 4 小时推一次读数──▶  cems_reading（瞬时速率 + 累计排放）
        │
        ▼  （定时任务，默认 60s 滚动一次）
滚动核算：年度累计排放 / 滚动日均速率 / 按速率外推期末排放
        │
        ▼
配额比对：预计期末缺口 = 预测期末排放 − 已分配配额
        │
        ▼
履约风险：缺口 > 配额 10% → 高风险；> 0 → 中风险；否则低风险
        │
        ▼
动态预警：命中阈值自动写入 alert_record（同企业同类预警不重复产生）
```

- **采数幂等**：`(企业, 排口, 采样时刻)` 唯一，重复采数不会造成累计值漂移；
- **可复现的模拟实测**：以企业本年度配额为锚生成确定性排放曲线，使多数企业期末排放落在配额附近、少数超排触发预警（实测：高 13 / 中 14 / 低 33），贴近真实碳市场分布；
- **与静态上报互证**：动态核算与季度上报同为 tCO₂e 口径，两条路径可相互印证。

## 九、关键设计取舍与不足

**取舍：为什么区块链与业务库仍放在同一个 MySQL 实例？**
本作业是单机演示环境，同库便于对照"改库 vs 改链"。需要说明的是：本项目已按联盟链范式实现 **5 个成员节点各自持链副本**（`chain_node_replica`，见 [4.7](#47-联盟链成员治理与链副本同步)），主链与各副本的链顶哈希实时比对 —— 任一节点本地库被篡改，其副本将因链顶不一致而被发现。真正投产时，应把各成员节点的库**物理分离**并接入 P2P 网络层，本项目先把"准入 + 出块权 + 多副本比对"的治理语义落到了单实例中。

**已完成的加固（对应早期自评的不足）：**
1. ✅ 共识由 PoW 挖矿升级为 **PoA 授权证明**，落地**多成员节点 + 准入白名单 + 出块权授予/吊销 + 链副本同步**（`consortium`）—— "联盟链"名副其实；
2. ✅ 排放数据接入 **CEMS 在线监测准实时采数 + 滚动核算 + 动态配额缺口预警**（`dynamic`）—— "动态核算"名副其实；
3. ✅ 碳资产由单一"配额"扩展为 **配额 + 碳信用（CCER / 林业碳汇 / 绿证）** 两类，并支持碳信用抵销履约（`credit`）—— "碳资产"名副其实；
4. ✅ 撮合引擎已接入 `db.tx()` 事务 + `SELECT ... FOR UPDATE` 行锁，消除并发超卖；并加登录限流、CORS 白名单、scrypt 口令摘要、私钥库 AES-256-GCM 加密、生产环境强校验关键密钥。
5. ✅ **线上安全默认已收紧**：演示账号接口在「生产 / 托管云平台」下**默认关闭**（仅显式 `DEMO_ACCOUNTS=true` 才开放）；生产环境未配置跨域白名单时**不再下发任何跨域放行头**（旧实现回显任意 `Origin`，配合 `Access-Control-Allow-Credentials: true`，等于允许任意第三方站点携带用户凭据读取接口）。同时新增**云平台探测**（`RENDER` / `DYNO` / `FLY_APP_NAME` / `VERCEL` / `RAILWAY_ENVIRONMENT` / `K_SERVICE`），**即便漏设 `NODE_ENV=production`，线上也不会裸奔** —— 详见 [docs/线上更新指引.md](docs/线上更新指引.md)。

**仍待完善（诚实的边界）：**
1. 各成员节点的链副本仍与业务库同实例，未实现**跨机器 P2P 广播**与网络分区容错（分区下无最终一致性保证）；
2. 接口限流为**进程内内存**实现，多实例部署时应改为 Redis 等共享存储；
3. 业务数据仍以**明文快照上链**，真实场景应改为"链上存哈希 + 链下加密存储"或引入零知识证明；
4. 无自动化测试 / CI、无容器化部署产物、无结构化日志与监控（见 [docs/部署说明.md](docs/部署说明.md) 的后续规划）。

## 十、常见问题

**Q：启动报 `Unknown database 'carbon_chain'`？**
先执行 `npm run initdb`。

**Q：中文在命令行里显示为乱码？**
Windows 控制台默认代码页为 GBK。使用 `start.bat`（已内置 `chcp 65001`），或先执行 `chcp 65001`。

**Q：初始化时间较长？**
正常现象。`npm run initdb` 会真实执行 900+ 次 ECDSA 签名、163 次 PoA 出块、23,892 条 CEMS 实测读数与首轮滚动核算，实测约 4 秒。

**Q：端口 8300 被占用？**
`set PORT=8400` 后重新启动。

**Q：想清空重来？**
`npm run initdb` 会 `DROP DATABASE` 后完整重建，可反复执行。

篡改—修复闭环实测输出（脚本默认篡改链尾附近的区块，故只需重做少量区块）：

```
✔ 模拟篡改区块 #162      → valid=false 异常数=3

```

> 篡改会被 **3 类校验**同时命中：区块内容哈希失配、PoA 出块签名失效、Merkle 根与交易表不符。
> 由于本链采用 PoA（无挖矿），单机"重算哈希 + 重新签名"本身很快；PoA 的防篡改威慑不靠算力成本，
> 而靠**签名与多副本比对**——被改动的后缀区块签名无法由授权节点之外的主体伪造，且链顶哈希一旦
> 与其它成员节点的副本不一致，立刻会被发现（见 [4.7](#47-联盟链成员治理与链副本同步)）。

5 项交互回归：登录页真实填表登录 → 行点击打开上报详情弹窗 → 浏览器点入区块详情 → 监管预警打开处置弹窗 → 企业端打开链上存证核验弹窗（4 项 PASS 结论 + Merkle 证明路径）。

### 11.3 性能采样 · 10 个接口 × 20 次

| 接口 | 平均 | P95 |
| --- | --- | --- |
| `/api/health` | 3.7 ms | 16 ms |
| `/api/chain/validate`（全链 163 区块、953 笔存证，**含 PoA 逐块 ECDSA 验签**） | 54.4 ms | 79 ms |
| `/api/enterprise/overview` | 4.5 ms | 6 ms |
| `/api/enterprise/reports` | 1.6 ms | 3 ms |
| `/api/regulator/statistics` | 12.6 ms | 19 ms |

（其余接口见 `artifacts/perf-report.md`）

> 说明：升级为 PoA 后，全链校验在原有"重算哈希 / 前向引用 / Merkle 根"之外，**新增了每个区块的出块签名验签**（163 次 ECDSA 验签），因此 `/chain/validate` 由原来的数毫秒上升到约 55 ms。这是"用签名替换挖矿"的代价：校验更重，但不消耗算力、出块瞬时完成。
