# 三闭环账号体系设计 · 全企业覆盖（2026-10-30）

> 任务：设计各类型账号，使六十余家企业全部形成业务闭环。
> 约束：① 原闭环账号之间封闭，不再接入其他机构（管理员端除外）；
> 　　　② 管理员类型账号仅 1 个，可跨企业管理；
> 　　　③ 其余类型账号按数量均分。

---

## 一、总体架构：「1 管理员 + 3 个互不连通的闭环」

```
                       ┌────────── admin ×1（唯一管理员，跨闭环运维/审计）──────────┐
                       │                                                            │
  ┌── 原闭环（封闭）──┐│  ┌─ 闭环 B（28 家）─┐     ┌─ 闭环 C（28 家）─┐            │
  │ 4 家真实焚烧企业   ││  │ 28 家合成企业     │     │ 28 家合成企业     │            │
  │ ent_zjbd/yfkw/    ││  │ ent001~ent030     │     │ ent031~ent060     │            │
  │ yxyf/zjyls        ││  │                   │     │                   │            │
  │ 监管 reg001       ││  │ 监管 reg002       │     │ 监管 reg003       │            │
  │ 核查 ver_cz_review││  │ 核查 唐山机构      │     │ 核查 河北绿链机构  │            │
  │   （沧州 org 8）  ││  │  ver_ts_clerk /   │     │  ver_hblv_clerk / │            │
  │ 交易 trader01     ││  │  ver_ts_review    │     │  ver_hblv_review  │            │
  │ （授权 ×4）       ││  │ 交易 trader02     │     │ 交易 trader03     │            │
  └───────────────────┘│  └───────────────────┘     └───────────────────┘            │
                       └────────────────────────────────────────────────────────────┘
```

三个闭环之间**没有任何共享的服务账号**：监管、核查机构、交易席位互不复用，
业务数据（任务归属、代理授权、配额流转）各闭环自洽。唯一横跨全部闭环的是
admin 的运维/审计视角（用户管理、链浏览器、审计台账），不做业务决策 ——
满足「管理员仅 1 个且可接入诸多企业」。

## 四、封闭的实现机制（要求①）

封闭不是口头约定，三层落地：

1. **核查派单（代码强制）**：`routes/enterprise.js assignVerifier` 对非四家
   真实企业的新上报，派单时排除沧州(8)与大连(1)（`pickVerifier(…, {exclude})`，
   见 `services/derive.js`）——新任务只会落在唐山(45)/绿链(54)之间按负荷均分，
   原闭环的核查席不会再吸收外来任务。
2. **交易授权（数据强制）**：trader01 名下仅 4 条授权（四家真实企业），
   `resolveActor` 按 `trade_mandate` 校验，未授权企业的交易请求 403。
   trader02/03 的授权只覆盖各自闭环的 28 家。
3. **存量清理（数据强制）**：沧州机构原本卡着 2 个外来企业任务
   （ent25 PROCESSING / ent38 PENDING），已按所属闭环迁出（org 45 / 54），
   `org 8 在办外来任务 = 0`。

监管端（reg001/002/003）在系统层面可见全平台（监管是公共职能），
「分管 28 家」为台账分工约定，演示动线按闭环走。

## 五、闭环业务（2025 履约年度，与原闭环同构）

每个闭环的年度闭环 = 分配 → 申报 → 核查（两段式双人，强制换人）→
缺口调剂/交易 → 清缴出证，全部动作经真实 API 执行并上链：

- **申报核查**：56 家企业 2025 年 4 个季度共 224 份上报单，结论草稿由
  种子数据遗留为「任务 DONE 但结论未批」的自相矛盾状态；本次将任务
  重开为 VERIFYING 并按闭环重指派，由闭环审核岗逐份批准（FAIL 按规则
  改判 REJECTED 并触发预警，其排放不计入履约认定值）。
- **缺口处理**：39 家企业核定排放超出 2025 分配。缺口大户（结算资金充足、
  缺口 ≤ 闭环内盈余）由交易席位代理购入本闭环盈余企业的配额（DvP 交割）；
  其余企业由闭环监管「年中调剂」增发补足。
- **清缴出证**：56 家全部执行 2025 清缴单 → SURRENDERED + 履约凭证上链。

编排脚本（幂等，可重放）：
`tools/fleet-accounts-setup.mjs` → `tools/fleet-tasks-reassign.mjs` →
`tools/fleet-loop-2025.mjs`（阶段 A 授权 / B 批准 / C 调剂 / D 交易 / E 清缴）。

## 八、本次修复的缺陷

1. **撮合交割年度漂移（P1，阻塞级）**：`trade_order` 不保存 vintage，
   `executeDeal` 用「双方账户交集、偏好当前年」重算交割年度 —— 舰队企业
   都有 2026 账户，2025 vintage 的卖单被拿去对 2026 交割，「卖方配额冻结不足」
   让整批撮合饿死。修复：`trade_order` 增加 `vintage_year` 列
   （`db/16_schema_trade_vintage.sql`），下单落库、交割优先采用；
   无标记的历史订单回退「卖方冻结配额所在年度 ∩ 买方账户」。
2. **结论草稿缺经办人（P2）**：种子数据的 224 份草稿 `submitted_by=NULL`，
   `assertDualControl` 正确地拒绝批准（"缺少另一方签字位"）。
   已按闭环补齐经办人 = 各机构录入岗（ver_ts_clerk / ver_hblv_clerk），
   双人链记录自此完整：录入岗出稿 → 审核岗批准。
3. **撮合行锁瞬断（P3）**：连续大批量交割时偶发 DvP 失败被 `si++` 跳过，
   重跑 `match()` 即消化（幂等）。批量场景建议循环调用至订单簿清空
   （脚本已内置）。
