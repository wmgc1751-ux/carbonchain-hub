## 3. 部署步骤（可复现）

```bash
# ① 基础依赖
apt-get update && apt-get install -y mysql-server-8.0 mysql-client-8.0 git curl nginx
curl -fsSL https://deb.nodesource.com/setup_22.x | bash - && apt-get install -y nodejs
fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile

# ② 账本独立实例（3307）—— Ubuntu AppArmor 必须放行，否则 socket/数据目录被拒
mkdir -p /var/lib/mysql-ledger /var/log/mysql-ledger
chown -R mysql:mysql /var/lib/mysql-ledger /var/log/mysql-ledger
cat > /etc/apparmor.d/local/usr.sbin.mysqld <<'AA'
/var/lib/mysql-ledger/ r,
/var/lib/mysql-ledger/** rwk,
/run/mysqld/** rwk,
/var/log/mysql-ledger/ rw,
/var/log/mysql-ledger/** rwk,
/etc/mysql/ledger.cnf r,
AA
apparmor_parser -r /etc/apparmor.d/usr.sbin.mysqld
mysqld --initialize-insecure --user=mysql --datadir=/var/lib/mysql-ledger
# my.cnf: port=3307, datadir=/var/lib/mysql-ledger, socket=/run/mysqld/ledger.sock,
#         pid-file=/run/mysqld/ledger.pid, mysqlx=0
# systemd unit: RuntimeDirectory=mysqld-ledger, Restart=always

# ③ 账号（Ubuntu 的 root 用 auth_socket，业务/账本账号分别建立）
mysql -u root -e "CREATE USER 'cc_biz'@'127.0.0.1' IDENTIFIED BY '...'; GRANT ALL ON carbon_chain.* TO 'cc_biz'@'127.0.0.1';"
mysql -h127.0.0.1 -P3307 -u root -e "CREATE USER 'cc_ledger'@'127.0.0.1' IDENTIFIED BY '...'; GRANT ALL ON carbon_chain_ledger.* TO 'cc_ledger'@'127.0.0.1';"

# ④ 数据还原（快照来自本地权威链）
mysql -u root carbon_chain < carbon_chain-final-20261031.sql
mysql -h127.0.0.1 -P3307 -u root carbon_chain_ledger < carbon_chain_ledger-final-20261031.sql

# ⑤ 部署应用
git clone --depth 1 https://github.com/wmgc1751-ux/carbonchain-hub.git /opt/carbonchain-hub
cd /opt/carbonchain-hub && npm install --omit=dev
# .env：NODE_ENV=production、DB_*、LEDGER_DB_*、JWT_SECRET/HJ212_PW/KEYSTORE_SECRET 均为随机强值
systemctl enable --now carbonchain      # ExecStart=node server/scripts/start-prod.js

# ⑥ nginx 反代（含 WS Upgrade 与 SSE 不缓冲）
nginx -t && systemctl reload nginx
```

## 5. 遇过的问题（备查）

1. **AppArmor 阻止 mysqld 写自定义路径** → 报 `Can't create directory` / `Unable to setup unix socket lock file`。修法：写 local profile 规则并用 `apparmor_parser -r` 重新编译（仅 `systemctl reload apparmor` 不生效）。
2. **Ubuntu 的 root@3306 用 auth_socket** → 远程 `-h127.0.0.1` 登录报 1698。修法：本机 socket 认证执行授权，业务走独立账号。
3. **mysqlx 端口 33060 与主实例冲突** → 账本实例加 `mysqlx=0`。
4. **SSH 多行 heredoc 被 shell 引号吞掉** → 改为本地写脚本 + `scp` + 远程 `bash` 执行。

## 7. 小程序后端并入（2026-10-31 追加）

小程序后端 `carbonchain-mini` 已部署到同机（8100，systemd `carbonchain-mini`），
并通过 `src/chainProxy.js` 将**链类只读查询**转发至权威链：

| 小程序端点 | 转发目标 | 说明 |
|---|---|---|
| `GET /mini/v1/chain/stats` | `/api/chain/stats` | 形状适配为 mini 契约（blocks/height/txs/head） |
| `GET /mini/v1/chain/blocks` | `/api/chain/blocks` | 分页结构 → 数组 |
| `GET /mini/v1/chain/blocks/:h` | `/api/chain/blocks/:h` | 含块内交易 |
| `GET /mini/v1/chain/tx/:id` | `/api/chain/tx/:id` | 含 Merkle 路径与签名校验结果 |
| `GET /mini/v1/chain/audit` | `/api/chain/validate?fresh=1` | 全链复算 |
| `GET /mini/v1/common/health` | `/api/chain/stats` | **口径与 stats 同源**（避免两套链高） |

**失败语义**：权威链不可达时返回 503 / `source='unavailable'`，**不回落到本地 SQLite 链**
—— 那会重新制造"两个链高"的问题。

**业务查询**（企业/上报/配额/核查/预警/公告）仍走 mini 本地 SQLite（15 表），
与链无关；写链（`POST /chain/verify` 等）未纳管，仍按原逻辑处理。

nginx 分流：

```
http://<host>/mini/  → 127.0.0.1:8100   （小程序 API）
http://<host>/       → 127.0.0.1:8300   （平台 Web/API，含 WS/SSE）
```

**验收（2026-10-31）**：
- `mini/v1/chain/stats` → `blocks=2152, height=2151, tip=28ed9075…`，与平台逐字节一致；
- `mini/v1/chain/blocks` → 返回 2151/2150… 真实区块（proposer=node-auditor-01）；
- `mini/v1/chain/audit` → 2152 块全链复算，`errors=[]`，`txPayloadBindingMismatch=0`；
- `mini/v1/common/health` → chain 字段与 stats 同源（此前 health 报本地 159 块，已修正）。
