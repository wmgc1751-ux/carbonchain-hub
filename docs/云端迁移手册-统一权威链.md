# 云端迁移手册 —— 统一权威链 · 五约束落地
=================================================================================
2026-10-27 定稿。对应五条硬约束：
  ① 不可以静态演示/快照，必须实时
  ② 笔记本关机，线上可用（24/7）
  ③ 全作品统一一条权威链
  ④ 避免额度问题（D1 日限额类天花板不得复现）
  ⑤ 数据不可以减少（全量迁移，逐表校验）

数据基线（已固化并验证可还原）：`D:/workspace/Challenge Cup/migration-baseline/`
  · business-3306-full.sql   359.5 MB —— 业务库全量（60 企业/上报/CEMS 7.5万+/
                             真实层 33.9万行/MRV/结算……15 张以上业务表）
  · ledger-3307-full.sql      1.95 MB —— 账本库全量（707 块/1,454 笔，已实测
                             还原演练通过，链顶哈希一致）
  ⚠ 还原时注意：dump 内含 `USE carbon_chain_ledger`，会按库名自建——
    指定其他目标库名时需先对 dump 做同名替换（本轮已验证过一次失败教训）。

权威链口径：本地 MySQL 账本（707 块）为迁移源与唯一权威。迁移后云端账本
即为权威链本体；本地降级为开发实例。

## 形态 A（推荐）：Oracle Always Free 单 VM 全自托管
---------------------------------------------------------------------------
资源：1 台 VM.Standard.A1.Flex（4 OCPU/24GB，永久免费）——Node 与双 MySQL
同机部署。可选第二台免费 VM 做账本独立主机（隔离强度升至跨主机 L3）。

前置（需你完成，约 30 分钟）：
  1. 注册 Oracle Cloud（需信用卡验证；Always Free 不扣费）
  2. 创建 A1 实例：Ubuntu 22.04，上传 SSH 公钥，开放 22/80/443 端口
  3. （可选）第二台 A1 实例，同上

执行（我可远程完成，或按本手册手动执行）：
  1. VM 内安装 MySQL 8 与 Node 22：
       sudo apt update && sudo apt install -y mysql-server-8.0
       curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash - && sudo apt install -y nodejs
  2. 双实例账本（L2/L3）：
       · 业务实例沿用 3306（apt 默认安装即是）
       · 账本实例初始化第二份 datadir 并监听 3307：
         sudo mysqld --initialize-insecure --datadir=/var/lib/mysql-ledger
         （systemd 单元模板见附录 A）
       · 各自创建独立账号（业务账号/账本账号分离——隔离强度按 L2 起步，
         双 VM 或分账号后如实升级 L3）
  3. 还原数据（从 migration-baseline/， scp 上传后）：
       mysql -u root -p < business-3306-full.sql     # 注意含 USE carbon_chain
       mysql -u root -p < ledger-3307-full.sql       # 注意含 USE carbon_chain_ledger
       还原后校验：node tools/migrate-verify.mjs（见 §校验）
  4. 部署 Node 后端：
       git clone https://github.com/wmgc1751-ux/carbonchain-hub.git
       cd carbonchain-hub
       # .env 模板见 §环境变量；LEDGER_DB_* 指向本机 3307
       npm ci --omit=dev && node server/scripts/start-prod.js
       （systemd 常驻单元见附录 A；listen 127.0.0.1:8300）
  5. HTTPS 接入（二选一）：
       a. cloudflared tunnel（推荐：不开公网端口，Cloudflare 网络直达 VM）
          cloudflared tunnel login
          cloudflared tunnel create carbonchain
          # 两条 ingress：www.carbonchain.dpdns.org → http://localhost:80 (nginx 静态)
          #              api.carbonchain.dpdns.org → http://localhost:8300 (Node)
          # 或直接 8300 一条隧道（Node 同时服务静态与 API，同端口形态）
       b. Nginx + certbot（VM 直开 80/443）
  6. DNS：dpdns.org 控制台把 www 与 api 的记录指向隧道/VM 公网地址
  7. Nginx 静态：dist/ 由 pack:static 产出，Node 亦可托管（现有代码即支持）——
     最简形态：**Node 单进程同端口托管静态+API，云上与本地形态一致**，
     Pages 不再承载 API，只留 CDN 分发（或整体退役，见 §边缘层退役）

验证（全部通过才算迁移完成，缺一即回滚 DNS）：
  · node tools/migrate-verify.mjs     # 双实例逐表行数 + 链顶哈希（§校验）
  · curl https://api.<域>/api/chain/validate?fresh=1    # 全链复算通过
  · curl https://api.<域>/api/chain/trust-model         # level 如实（云上单 VM = L2）
  · 小程序登录 + 上报 + 验真（真机/开发者工具）
  · **关机测试**：本地笔记本关机后，以上全部复测通过（约束②的验收动作）

## 形态 B：TiDB Serverless 双免费集群 + Node 托管（免信用卡路线）
---------------------------------------------------------------------------
资源：TiDB Serverless 免费 ×2（业务/账本各一，邮箱注册）；Node 托管任选
（Render 免费档会休眠约 50s 冷启动——可用但首访慢；或同形态 A 的 Oracle VM
只跑 Node 不装 MySQL）。数据在托管库，配额为 request units（本负载轻）。

与形态 A 的差异：
  · 数据库：MySQL → TiDB（MySQL 兼容；config.js 的 DB_SSL=no-verify +
    DB_MANAGED=true 路径已支持，无需改代码）
  · 隔离强度：双集群同账号 = L2；如需 L3，注册两个 TiDB 组织（两个邮箱）
  · 额度形态：从"自建无配额"变为"按用量计费单位"——聚合物化表与
    读缓存已把单次请求的行读压到低位，但它是"用量计费"，天花板比
    自建低。若出现额度压力，加一层 Cloudflare Worker 只读缓存（30s）
    即可把重复读全部吸收。
  · 迁移工具：TiDB 不接受 mysqldump 全量直灌的某些语法（DEFINER 等），
    用 node tools/migrate-to-turso.mjs 的同款分批管道改写为 TiDB 目标端
    （脚本骨架已在库中，改目标端连接与方言即可）。

## 边缘层退役（两形态通用，切换成功后执行）
---------------------------------------------------------------------------
  1. 停用 worker 的两个 cron（*/30 出块/预聚合、17 3 清理）——
     数字分叉的源头即此；wrangler.worker.json 删除 triggers 后重部署。
  2. www 的 /api/* 改为代理权威后端：
     · 方式一：Pages Functions（functions/api/[[path]].js）改为 fetch 权威后端
       （环境变量 BACKEND_URL 注入），或
     · 方式二：DNS 把 www 的 /api 路由直接指向权威后端域名（最简）。
  3. D1（carbonchain_platform）与 Turso 独立链退役：数据导出归档后解绑。
     退役后全作品**仅剩一条链**——约束③落地。
  4. workers-d1 上的 771 块链为 cron 产生的边缘演示实例，不含权威数据，
     归档后随 D1 退役；论文口径以权威链为准。

## §校验 —— migrate-verify.mjs 的验收清单
---------------------------------------------------------------------------
  · 业务库：15+ 张表逐表行数比对（本地迁移前快照 vs 云端）
  · 账本库：逐表行数 + 链顶（block_index, block_hash）一致
  · 抽样：每表首/末行全字段比对
  · 运行时：/api/chain/validate?fresh=1 全链复算通过
  · /api/chain/business-binding：业务行与链上摘要全部一致
  · 关机测试（约束②验收）：本地关机后以上全部重跑通过
  · 三端口径：www、小程序、API 三处链高度读数一致（约束③验收）

## 附录 A：systemd 单元要点
---------------------------------------------------------------------------
  · mysqld-ledger.service：mysqld --defaults-file=/etc/mysql/ledger.cnf
    （datadir=/var/lib/mysql-ledger, port=3307）
  · carbonchain.service：node server/scripts/start-prod.js，
    Environment=NODE_ENV=production，Restart=always
  · cloudflared.service：cloudflared tunnel run carbonchain
  三者 enable --now，并配置相互 After= 依赖（账本 → 业务 → Node）。

## 附录 B：回滚
---------------------------------------------------------------------------
  · 迁移期间本地双实例不动——云端验收不通过时，DNS 切回本地隧道即
    恢复原状，零数据损失。
  · 云端数据异常时，从 migration-baseline/ 重新还原即可（幂等）。
