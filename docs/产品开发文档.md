## 1. 项目概述

### 1.1 一句话定义

**碳链通**是一个面向全国碳排放权交易市场的四端协同平台：控排企业在线申报碳排放数据，第三方核查机构在线核查并出具报告，生态环境主管部门在线分配配额、监控交易与处置预警，社会公众可免登录查看公示大屏并独立核验链上存证。所有关键业务动作（上报、核查、分配、成交）都以**企业/机构/监管各自的私钥签名后上链存证**，形成不可篡改、可第三方独立验证的碳数据账本。

### 1.2 选题如何避开"雷同项"

课程要求明确排除图书管理、点餐、二手交易一类题目。本项目选题具备三重差异：

1. **业务领域有真实制度背景**：全国碳市场已覆盖八大高排放行业，数据质量直接决定配额与真金白银，痛点清晰（企业自申报、可事后修改、责任难界定）。
2. **区块链不是"贴图式"装饰**：链上只承载"存证 + 签名 + 时间戳"，解决的是**数据来源不可抵赖、报告签发后不可篡改、配额流转全程留痕**这三个传统中心化系统解决不了的问题。
3. **四端职责分离**：企业端 / 核查机构端 / 监管端 / 公众端，四套菜单、四类权限、四种数据视角，且**不同角色使用不同私钥签名同一份业务数据**，链上可区分责任主体。

### 1.3 技术内核（自研，零区块链第三方库）

| 能力 | 实现方式 |
| --- | --- |
| 哈希链 | SHA-256，`block_hash = SHA256(index + prev_hash + merkle_root + nonce + difficulty + tx 指纹集 + 时间戳)` |
| 工作量证明 | 前导零难度（当前 4），`nonce` 递增碰撞；实测单区块平均出块 76 ms，最大 469 ms |
| Merkle 树 | 交易两两配对哈希向上归并，偶数补尾；提供**存在性证明路径**（`{position, hash}` 列表）供任意第三方复算根哈希 |
| 数字签名 | secp256k1 ECDSA（Node 内置 `crypto`），DER 编码；同一业务数据由不同角色私钥签名，链上可区分责任人 |
| 钱包 | 公钥 → SHA-256 → RIPEMD-160 → `0x` + Base58Check 风格地址；**私钥离线托管在 `server/keystore.json`，绝不落业务库** |
| 全链校验 | 四道关：逐块重算内容哈希 → 校验前驱指针链 → 校验 PoW 难度达标 → 复算 Merkle 根 |

## 4. 区块链子系统设计（本项目技术核心）

### 4.1 区块与交易

**区块（`chain_block`）**

| 字段 | 说明 |
| --- | --- |
| `block_index` | 区块高度（唯一） |
| `block_hash` | 区块内容哈希（SHA-256），参与下一区块的前驱指针 |
| `prev_hash` | 前一区块哈希，构成哈希链 |
| `merkle_root` | 本区块交易集的 Merkle 根 |
| `nonce` / `difficulty` | 工作量证明随机数与难度（前导零个数） |
| `tx_count` / `size_bytes` / `mine_time` | 打包交易数、区块字节数、出块耗时（毫秒） |
| `miner` / `block_time` | 出块节点标识与出块时间 |

**交易（`chain_tx`）** 五类业务存证：

| `tx_type` | 业务含义 | 条数 |
| --- | --- | --- |
| `EMISSION_REPORT` | 企业排放上报存证 | 341 |
| `VERIFY_REPORT` | 核查报告存证 | 273 |
| `QUOTA_ALLOC` | 配额分配存证 | 150 |
| `TRADE_DEAL` | 交易成交存证 | 90 |
| `ENTERPRISE_REG` | 企业纳入控排备案存证 | 60 |

交易字段包含：`tx_id`（交易哈希）、`biz_no`（业务单号）、`from_address` / `to_address`、`payload_hash`（业务数据规范化后的哈希）、`signature`（发起方私钥签名）、`pub_key`、`block_index`、`nonce`、`gas_fee`、`status`。

### 4.2 上链流程（`services/anchor.js`）

```
业务动作（提交上报 / 签发报告 / 下发配额 / 成交）
   ↓ 业务表落库（链下）
   ↓ 组装存证载荷 payload（业务主键 + 关键字段 + 时间戳）
   ↓ 规范化序列化（键排序 + 无空格 JSON）→ SHA-256 → payload_hash
   ↓ 用发起方私钥 ECDSA 签名 → signature
   ↓ 入交易池（chain_mempool 视图 / 内存池）
   ↓ 出块：打包 → 算 Merkle 根 → PoW 碰撞 nonce → 写 chain_block + chain_tx
   ↓ 回写业务表的 chain_block_index / chain_tx_id（链下锚定链上）
```

### 4.3 Merkle 存在性证明

任意第三方拿到「交易哈希 + 证明路径」，无需下载全链即可复算 Merkle 根并比对区块头：

```
leaf  = SHA256(tx)
level = leaf
for step in path:            # path: [{position: 'left'|'right', hash}]
    level = position == 'left'
          ? SHA256(step.hash + level)
          : SHA256(level + step.hash)
assert level == block.merkle_root
```

系统在交易详情页与存证核验弹窗中都直接展示该路径；当某区块仅含一笔交易时，Merkle 根等于该交易哈希，页面会明确提示"单叶场景，无需兄弟节点即可自证"。

### 4.4 全链完整性校验（四道关）

`GET /api/chain/validate` 依次执行：

1. **内容哈希关**：逐块重算 `block_hash`，与库中记录比对；
2. **前驱指针关**：逐块校验 `prev_hash == 前一块 block_hash`，断链立即暴露；
3. **难度关**：校验 `block_hash` 前导零个数 ≥ `difficulty`，防止篡改后敷衍了事；
4. **Merkle 关**：复算每块交易集的 Merkle 根，与区块头比对。

任一道关失败都会返回异常清单（区块高度 + 原因 + 期望值/实际值），前端在浏览器页面以红色异常列表展示。

### 4.5 防篡改实验台（答辩演示重点）

| 步骤 | 操作 | 实测结果 |
| --- | --- | --- |
| 1 | `POST /api/chain/tamper` 篡改区块 #10 | 校验立即 `valid=false`，异常数 2；首条异常："区块 #10 内容哈希与记录不符：期望 `78230a4569ce0b9a…`，实际 `0000833dd2fee572…`" |
| 2 | `POST /api/chain/repair` 一键修复 | 修复 150 个区块、重做工作量证明总耗时 **10574 ms**，修复后 `valid=true`、异常数 0 |
| 3 | 观察副作用 | 被篡改区块及其后**所有区块哈希全部改变** —— 直观量化"篡改成本极高且必然被全网察觉" |

### 4.6 签名与责任分离

| 业务动作 | 签名主体 | 链上可验证的结论 |
| --- | --- | --- |
| 排放上报 | 企业私钥 | 该数据确由该企业提交，事后不可否认 |
| 核查报告 | 核查机构私钥 | 该结论确由该机构签发，签发后内容不可改 |
| 配额分配 | 监管节点私钥 | 分配动作确由主管部门作出，全程留痕 |
| 交易成交 | 买方/卖方私钥 | 成交价量与链上时间戳一致，账实相符 |

私钥以加密 keystore 形式存于 `server/keystore.json`，业务表只存公钥与地址 —— 即使业务库被拖库，也无法伪造签名。

> 全部 16 张表均满足"每表 50 条以上假数据"的要求；链上两表的数据不是"假造"的，而是 `init-db.js` 真实跑 PoW 出块得到的。

### 5.2 关键设计点

- **链上链下分表**：业务表（`emission_report` 等）承载查询与统计；存证表（`chain_block`/`chain_tx`）承载不可篡改的锚点。业务表用 `chain_block_index` / `chain_tx_id` 反向指向链上，形成"链下可查、链上可证"的双层结构。
- **口令安全**：`password = SHA256(salt + 明文)`，每账号独立随机盐，不存明文。
- **幂等约束**：`emission_report` 对 `(ent_id, year, quarter)` 做业务级唯一校验，避免重复上报。
- **索引策略**：链上两表对 `block_index`（唯一）、`block_hash`、`tx_id`、`block_index+from_address` 建索引，保证浏览器分页与地址视图的查询效率。
- **快照字段**：组织名称等以快照方式冗余存储，避免历史记录随主数据改名而变化。

### 7.3 工程化细节

- **哈希路由 + 参数注入**：路由表 27 条，`:index` / `:txId` / `:id` 等参数以 props 注入视图组件，并以完整路径作为 `key`，保证"区块 A → 区块 B"时组件重新挂载、数据不串页。
- **角色路由守卫**：非本端路由自动提示并跳回本端工作台；未登录访问业务路由重定向到登录页。
- **会话与失效**：`localStorage` 持久化 JWT；任一请求返回 401 即清会话并跳登录。
- **请求缓存**：`App.cache` 提供 45 秒 TTL 的内存缓存，减少页面来回切换的重复请求。
- **统一格式化 / 字典**：`App.fmt`（千分位、万亿量级、百分比、相对时间、哈希缩写、字节）与 `App.DICT`（状态/类型/优先级等中文+配色）全站复用。
- **一致性设计语言**：暗色碳主题、渐变面积图、状态语义色（通过=绿、驳回=红、存证=链色），大屏/浏览器/工作台三套布局共用同一套 CSS 变量。

### 8.5 已修复的典型缺陷（开发过程留痕）

| 现象 | 根因 | 修复 |
| --- | --- | --- |
| 页面只剩骨架，内容区空白但控制台无报错 | Vue 3 的 `h('x-card')` 在渲染函数中**不会**查全局组件注册表，字符串标签一律按原生元素处理，于是 `<x-card>` 变成了空的自定义元素 | 在 `core.js` 提供组件名解析版 `h`（`App.h`），命中 `App.components` 时改传组件对象；7 个视图文件统一切换 |
| 区块详情 / 交易详情 / 公告详情打开即报"交易不存在" | 路由参数没有传给视图组件，组件内 `props.txId` 为 `undefined`，请求打到了 `/chain/tx/undefined` | 应用外壳按路由路径注入 props，并以 `router.path` 作 `key` 强制重新挂载 |
| 重复运行自检脚本，报"该季度已存在上报单" | 冒烟脚本硬编码 `2026/Q3`，而业务上该企业该季度唯一 | 脚本先读取已有上报单，自动挑一个空位周期；全部占满时输出 SKIP 而非 FAIL |
| 单笔交易区块的存证核验弹窗提示语义含糊 | 未区分"单叶无兄弟"与"数据缺失" | 弹窗按 `leafIndex/root/leafHash` 判断，明确提示单叶自证场景 |
| 演示期间服务进程可能被未捕获异常带走 | Node 15+ 未处理 Promise 拒绝会直接退出 | `server/app.js` 注册 `unhandledRejection` / `uncaughtException` 兜底，记日志但保持服务在线 |

## 附录 B. 论证要点（答辩备忘）

1. **为什么必须用区块链**：排放数据由被监管者自报自改，中心化数据库的"管理员权限"就是最大的风险点；链上存证让"谁在什么时候签了什么"不可抵赖。
2. **链上存什么、不存什么**：只存业务主键、关键字段摘要、规范化后的载荷哈希与签名，**原始明细留在链下库**，兼顾可信与性能。
