## 〇、2026-10-30 更新：全部角色收敛为「一类一个账号」（终版 8 个）

**结论：一个企业不需要诸多账号，一类角色也不需要诸多账号 ——
演示仅使用 8 个账号：`admin` · `reg001` · `ver_cz_review` ·
`ent_zjbd` / `ent_yfkw` / `ent_yxyf` / `ent_zjyls` · `trader01`
（口令均 `123456`，admin 为 `admin123`）。**

依据（代码 + 实测双重验证）：

1. **服务端鉴权只看角色不看岗位。** 全服务端没有一处按 `post`
   的权限校验（唯一的岗位硬校验在核查端 `checkPost`：录入需 ENTRY、
   批准需 REVIEW）；监管、交易、企业接口一律只按 role 放行。
2. **企业端单一主账号 13/13 走通全链路。** 用 `ent_zjbd` 实测：
   总览、上报单、配额、分析、钱包、MRV 填报、核算预览、清缴单、
   结算账户、交易挂单、代理授权全部 200（探针 `tools/_probe-one-ent.mjs`）。
3. **监管端 `reg001` 一席足够。** `checkPost` 不覆盖监管接口，
   配额分配 / 预警处置 / 批量清缴 / 公告全部可做（实测配额分配列表 165 行）。
4. **交易端 `trader01` 一席足够。** 其名下持有四家企业的 4 条代理授权
   （见下方「授权修复」），「授权 → 挂单」全链单席可演示。
5. **核查端保留 `ver_cz_review`（沧州机构审核岗）。** 这是唯一不能
   随意合并的一端：结论批准强制「批准人 ≠ 提交人」（`assertDualControl`），
   且岗位要求 REVIEW 职责位。四家企业的核查任务按机构隔离，
   归属沧州(8)/唐山(45)/绿链(54)三家，`ver001`（大连，org 1）名下无任务，
   故留任务最多、可受理+批准的 `ver_cz_review`。
   仅「提交结论草稿」一步需要录入岗 —— 如需现场演示完整两阶段，
   临时在 `server/routes/auth.js` 的 `DEMO_USERNAMES` 加回 `ver_cz_clerk` 即可。

**授权修复（本次附带）**：恢复脚本未重映射 `trader01` 的 user id 引用，
ent65 的代理授权 `trader_user_id=21` / `granted_by=13` 均为悬空引用，

全部上链（区块 #1139–1141）。trader01 名下现为 4 条 ACTIVE 授权。

**变更动作**：登录页演示白名单 25 → 14（企业端收敛）→ **8**（全角色收敛，
移除 `reg_review`、`ver001`、`ver_cz_clerk`、`ver_dl_clerk/review`、`trader02`、
`ent001*` 及四家的 `_clerk`/`_quota`）。被移除账号仍留库内
（历史审批链字段引用它们），只是不再提供登录入口。

**推荐演示动线（8 账号贯穿全平台）**：

## 四、本次修复的两个缺陷

### 1. 存证详情页 500（业务库与账本库来自不同部署批次）

业务库的 `chain_tx_id` 原本是**线上部署（Cloudflare Worker + Turso）那条链**的交易号，
本地账本（3307 独立实例）自然查不到。`/enterprise/reports/:id/chain` 与
`/verifier/reports/:id/chain` 直接解引用 `tx.pub_key`，一个空指针把「存证缺失」
说成了「服务器故障」。

- 代码：两处 `tx` 为空时返回 404 + 明确文案，不再 500
- 数据：`tools/reanchor-reports.mjs` 补锚 340 份上报单、
  `tools/reanchor-biz.mjs` 补锚 285 份核查结论 + 161 条配额分配 + 60 次清缴 + 1 条代理授权
- 结果：核心业务表存证命中率 100%，链上交易 289 → 1 138 笔

### 2. 账本库未随平台启动

`start.bat` 只拉起 `node server/app.js`，账本实例（3307）需另行启动。
账本库缺失时 `/api/health` 与 `/api/public/dashboard` 全站 500。

- 新增 `D:\MySQL\start-ledger.bat`（检测端口、拉起实例、轮询就绪）
- `start.bat` 启动前 `call` 它，已在运行则跳过
