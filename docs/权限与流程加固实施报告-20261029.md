## 二、P0：交易授权链路（修复可被直接利用的越权）

### 改造前后对比

```js
// ❌ 改造前（trade.js）
function traderEntId(req) {
  const explicit = req.body.entId || req.query.entId;
  return explicit || req.user.orgId;      // 直接采信客户端传入的 entId
}
// 后果：任何 TRADER 带上 entId=任意企业 即可代其挂牌/撤单/清缴

// ✅ 改造后
async function resolveActor(req, need = 'TRADE', amount = null) {
  // 企业端：操作自己
  if (req.user.role === 'ENTERPRISE') return { entId: req.user.orgId, mandate: null };
  // 交易端：必须有有效授权
  if (!explicit) throw new TradeAuthError(400, '交易端必须显式指定代理企业');
  const m = await db.one(`SELECT ... FROM trade_mandate
    WHERE ent_id=? AND trader_user_id=? AND status='ACTIVE'`, [explicit, req.user.id]);
  if (!m) throw new TradeAuthError(403, '该企业未授权本机构代理交易');
  if (m.expired) throw new TradeAuthError(403, '授权已过期');
  if (need === 'OFFSET' && m.scope !== 'TRADE_AND_OFFSET')
    throw new TradeAuthError(403, '授权范围不含清缴');
  if (m.max_amount && amount > m.max_amount)
    throw new TradeAuthError(403, '超出授权额度上限');
  return { entId: explicit, mandate: m };
}
```

### 实测：6 个越权路径全部拦截

```
✔ 不带 entId 下单            → 400 必须显式指定代理企业
✔ entId=65 下单（未授权）    → 403 未授权本机构代理交易
✔ entId=66 下单（未授权）    → 403
✔ entId=65 查账户（未授权）  → 403
✔ entId=65 查委托（未授权）  → 403
✔ entId=65 清缴（未授权）    → 403
```

授权后：

```
✔ 查账户（有授权）           → 200 可访问
✔ 超额度下单 2000>1000       → 403 超出单笔上限
✔ 清缴（授权为 TRADE_ONLY）  → 403 授权范围不含清缴
```

### 配套

- **表**：`trade_mandate`（授权方、受托方、范围、额度、期限、链上锚点）
- **字段**：`trade_order.biz_type`（AGENCY/PROPRIETARY）、`mandate_id`、`reviewed_by`
- **接口**：`POST /api/mandate`（签发）、`/:id/revoke`（撤销）、`/mine`、`/ledger`（监管台账）、`/granted-to-me`（交易端可见）、`/candidates`
- **页面**：企业端「代理授权」、监管端「代理授权台账」
- **上链**：签发与撤销均产生 `TRADE_MANDATE` 交易

## 三、P1：内控与合规

- `sys_user.post` + `user_post_dict`（8 个岗位，含录入/审核/管理三个职责位）
- `integrity.checkPost(user, need, action)` 强制校验
- 实测：

```
✔ 录入员做审核 → 403 需要「审核」权限，当前岗位为「核查录入员」
✔ 审核员审核   → 放行
✔ 审核员做录入 → 403（职责分离）
```

### P1-2 双人复核

核查结论改为**两阶段**（经办提交 → 另一人批准）：

```
✔ 自己批自己 → 403 SELF_APPROVAL「不能由同一人经办并批准」
✔ 不同人批准 → 放行
✔ 缺签字位   → 400 DUAL_MISSING
```

复核签字位（`submitted_by` / `approved_by`）已写入链上负载，不可否认。

### P1-3 管理员权限收缩（发现并修复系统性问题）

### P1-4 资质互斥

- `org_qualification` + `qual_conflict_rule`（3 条规则，含法条依据）

## 八、最值得记住的一点

P0 的越权与 P1 的 ADMIN 旁路，本质是**同一种错误：把"方便"写进了权限判断**。
`return explicit || req.user.orgId` 和 `|| req.user.role !== 'ADMIN'` 都是为了让演示更顺而留的口子，
但在真实环境里，前者等于开放全部企业资产，后者等于审计者即被审计对象。

这两处现在都是**默认拒绝、显式放行**——缺少授权就 403，不在白名单就 403，没有"特殊情况"。
