> 依据：对当前代码与数据库的实地核查，非推测。每条标注 **【硬性风险】**（可被利用或违反合规，

## 一、【硬性风险 P0】交易端可操作任意企业的配额与资金

### 现状（代码级证据）

`server/routes/trade.js:21-26`：

```js
function traderEntId(req) {
  if (req.user.role === 'ENTERPRISE') return req.user.orgId;
  const explicit = req.body && req.body.entId ? Number(req.body.entId)
    : (req.query.entId ? Number(req.query.entId) : null);
  return explicit || req.user.orgId;   // ← 直接采信客户端传入的 entId
}
```

**这意味着**：`trader01` 账号（`org_id` 为空）登录后，只要在请求里带上 `entId=65`，
就能以河北恒能（保定）的名义挂牌、撤单、甚至触发清缴——而该企业从未授权给它。
`POST /api/trade/orders`、`/orders/:id/cancel`、`/offset` 三个写操作全部走这条路径。

**这不是"边界模糊"，是越权漏洞。** 在真实环境里，任何拿到交易端账号的人都能操纵全部企业的碳资产。

### 改进方案：三级授权链路

**第一级：企业主动授权（新增 `trade_mandate` 表）**

```sql
CREATE TABLE trade_mandate (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  ent_id BIGINT NOT NULL,              -- 授权方（企业）
  trader_user_id BIGINT NOT NULL,      -- 受托方（交易端账号）
  scope VARCHAR(20) NOT NULL,          -- TRADE_ONLY / TRADE_AND_OFFSET
  max_amount DECIMAL(18,3) DEFAULT NULL,  -- 单笔/累计额度上限
  valid_from DATETIME NOT NULL,
  valid_to DATETIME NOT NULL,
  status VARCHAR(16) DEFAULT 'ACTIVE', -- ACTIVE / REVOKED / EXPIRED
  granted_by BIGINT NOT NULL,          -- 企业侧授权人（须为填报员以上）
  revoked_at DATETIME, revoke_reason VARCHAR(200),
  chain_tx_id VARCHAR(80),             -- 授权动作本身上链
  UNIQUE KEY uk_mandate (ent_id, trader_user_id, scope)
);
```

**第二级：每次写操作强制校验（改 `traderEntId`）**

```js
async function traderEntId(req, needScope) {
  if (req.user.role === 'ENTERPRISE') return req.user.orgId;
  const explicit = ...;                       // 客户端声明的代理对象
  if (!explicit) throw new ApiError(400, '交易端必须显式指定 entId');
  const m = await db.one(
    `SELECT * FROM trade_mandate
      WHERE ent_id=? AND trader_user_id=? AND status='ACTIVE'
        AND NOW() BETWEEN valid_from AND valid_to`, [explicit, req.user.id]);
  if (!m) throw new ApiError(403, '该企业未授权本机构代理交易');
  if (needScope === 'OFFSET' && m.scope === 'TRADE_ONLY')
    throw new ApiError(403, '授权范围不含清缴');
  if (m.max_amount && amount > m.max_amount)
    throw new ApiError(403, `超出授权额度上限 ${m.max_amount} t`);
  return explicit;
}
```

**第三级：授权可视化与撤销**
- 企业端新增"代理授权"页：授权/撤销/查期限与额度；
- 监管端新增"授权台账"页：可查全部授权关系（谁授权给谁、范围、期限、是否撤销）；
- 授权与撤销动作本身**上链存证**（`chain_tx_id`），形成不可否认的记录。

### 自营 vs 代理的隔离

碳资产管理公司现实中既做代理也做自营，两者风险不同，必须分开：

| 类型 | 资金来源 | 配额来源 | 日志标识 | 风控 |
| --- | --- | --- | --- | --- |
| 代理业务 | 委托企业的结算账户 | 委托企业的配额 | `BIZ_TYPE=AGENCY` | 受 mandate 额度约束 |
| 自营业务 | 机构自有账户 | 机构自购配额 | `BIZ_TYPE=PROPRIETARY` | 需单独开通、单独风控额度 |

建议在 `trade_order` 增加 `biz_type` 字段，两类订单在委托单列表、成交记录、对账报表中分开呈现。
**当前产品只做代理，自营暂不开放**——但这层抽象要先留出来，否则将来加自营会污染代理数据。

## 二、【硬性风险 P1】单账号单点，无经办/审核分离

### 现状（数据库证据）

```
sys_user 表字段：id, username, password, salt, real_name, role, org_id, org_name, phone, status
→ 没有 post（岗位）、没有 reviewer_id、没有 level
org_id 多账号的机构：0 个
```

即：**每个企业/机构只有一个账号**。监管 1 个、核查 1 个、交易 1 个、企业各 1 个。

**三条硬伤**：
1. **单点停摆**：账号锁定/人员离职，该机构全部业务中断，无备用账号；
2. **无复核**：核查结论提交、配额清缴、大额挂牌这些"一人可定成败"的动作没有二次确认；
3. **不合内控**：碳市场核查机构按《碳排放权交易管理暂行条例》要求独立性，单人操作无法自证独立。

### 改进方案：角色池 + 岗位分级 + 关键操作双人复核

**① 岗位字段（或独立 `user_post` 表）**

```sql
ALTER TABLE sys_user ADD COLUMN post VARCHAR(24) DEFAULT NULL;  -- CLERK 录入 / REVIEWER 审核 / ADMIN 机构管理员
ALTER TABLE sys_user ADD COLUMN parent_user_id BIGINT DEFAULT NULL;  -- 子账号归属的主账号
```

**② 每个机构可建多个子账号**：主账号（机构管理员）负责开通/停用子账号；子账号按岗位分权：
- `CLERK`：录入、查询、提交草稿；**不能**提交核查结论、不能清缴；
- `REVIEWER`：审核、批准、提交最终结论；**不能**录入（避免自审自批）；
- 关键操作要求 `CLERK 提交 → REVIEWER 批准` 两人协作。

**③ 双人复核清单（哪些动作必须）**

| 动作 | 复核要求 | 实现要点 |
| --- | --- | --- |
| 核查结论上链 | 必须 | 已有 `verify_task` 可加 `submitted_by` / `approved_by` 两列，二者不可相同 |
| 配额清缴（surrender） | 必须 | `quota_surrender` 加 `initiated_by` / `confirmed_by` |
| 大额挂牌（阈值可配，如 ≥1000 t） | 必须 | `trade_order` 加 `reviewed_by`，未复核不允许 `OPEN` |
| 配额分配调整 | 建议 | 监管端内部双人 |
| 管理员日常业务操作 | 禁止 | ADMIN 角色在业务路由层直接拒绝（现在 ADMIN 能访问部分业务接口） |

**④ 管理员账号的边界（当前也有问题）**

现在 `admin` 可以调用很多业务接口（`requireRole('ADMIN','REGULATOR')` 多处）。按内控，
管理员应只见配置与运维，**不得参与**配额分配、核查结论、交易等业务决策——
否则"审计者即被审计对象"。建议在业务路由把 ADMIN 从 `requireRole` 中移除，仅保留在运维路由。

## 三、【硬性风险 P1】核查与交易的利益冲突无系统阻断

### 现状

代码中**不存在任何**"同一主体不能同时具备核查与交易资质"的校验。
`verifier_org` 与 `sys_user.role='TRADER'` 之间没有交叉约束。

**风险场景**：某机构既是核查机构（可出具 A 企业的核查结论），又代理 A 企业做交易
（知道核查结论后抢先交易），或更恶劣——帮 A 企业粉饰数据后自己交易牟利。
仅靠制度文件约束，在系统层面无法阻止。

### 改进方案：互斥资质校验（写时校验 + 定时巡检）

```sql
-- 机构资质表（统一核查/交易/清缴代理资质）
CREATE TABLE org_qualification (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  org_key VARCHAR(64) NOT NULL,        -- 统一社会信用代码或机构标识
  qual_type VARCHAR(24) NOT NULL,      -- VERIFIER / TRADER / SELF_TRADE
  status VARCHAR(16) DEFAULT 'ACTIVE',
  granted_at DATETIME, revoked_at DATETIME,
  UNIQUE KEY uk_qual (org_key, qual_type)
);
```

**校验规则（开启资质时触发）**：

```js
async function grantQualification(orgKey, type) {
  const conflictMap = { VERIFIER: ['TRADER', 'SELF_TRADE'], TRADER: ['VERIFIER'], SELF_TRADE: ['VERIFIER'] };
  const conflicts = conflictMap[type] || [];
  const hit = await db.query(
    `SELECT qual_type FROM org_qualification
      WHERE org_key=? AND status='ACTIVE' AND qual_type IN (?)`, [orgKey, conflicts]);
  if (hit.length) throw new ApiError(409,
    `资质互斥：该机构已持有 ${hit.map(h=>h.qual_type).join('/')} 资质，不可同时开通 ${type}`);
  await db.insert('org_qualification', { org_key: orgKey, qual_type: type });
}
```

**三层保障**：
1. **写时阻断**：开通资质时校验；
2. **定时巡检**：每日扫描已存在冲突组合，发现即告警到监管端（防历史数据绕过）；
3. **单笔交易抽查**：交易发生时校验「参与方是否为自己的核查客户」，命中则标记风险并记录。

第 3 条最实用：核对 `trade_deal.buyer_ent_id / seller_ent_id` 与该机构 `verify_task` 中的
被核查企业是否重合——重合即说明"给自己的客户做交易"，自动进入监管预警队列。

## 四、【体验优化 P2】企业端职责混合

### 现状

企业端一个角色承担：排放填报 → 数据上报 → 配额履约 → 交易下单 → 清缴。
企业内部的填报人（环保专员）与履约负责人（财务/碳资产经理）现实中通常是两个人。

### 改进方案：企业端子角色（`post` 字段复用）

| 子角色 | 权限 |
| --- | --- |
| `ENV_CLERK` 排放填报员 | 活动数据、排放上报、查看链上存证 |
| `QUOTA_MANAGER` 履约管理员 | 配额账户、交易下单、清缴、查看报表 |
| `ENT_ADMIN` 企业管理员 | 开通子账号、授权交易机构、查看全部数据 |

**收益**：日志可按岗位归集（"这条上报是谁填的、谁批的"），责任到人；
大企业可多人协作；与第二节的岗位分级共用一套机制，不额外增加复杂度。

## 五、【体验优化 P1】审计追溯需统一归集与全链路串联

### 现状（实测数据）

```
26 个路由文件 → 18 个写审计日志（69%）
audit_log 表记录：actor / action / target / result / ip / time
链上存证：197 板块 + 276 笔业务交易
```

**已有基础不错**，缺两点：
1. 8 个路由未写审计（覆盖不全，具体是哪些需逐个确认）；
2. **无跨角色串联**——监管要追溯一个企业的完整链条，得分别去企业端、核查端、交易端查日志。

### 改进方案：统一审计中心 + 一条链路视图

**① 补齐审计覆盖**：加一个启动自检，列出所有"有写操作但无 writeLog"的路由，作为回归项。

**② 全链路串联（核心）**

现有各表已有业务主键，可用「企业 + 年度」串起完整证据链：

```
活动数据(activity_data) → 排放上报(emission_report, chain_tx_id)
  → 核查结论(verify_report, chain_tx_id)
  → 配额分配(quota_allocation, chain_tx_id)
  → 挂牌/成交(trade_order / trade_deal, chain_tx_id)
  → 清缴(quota_surrender, chain_tx_id)
```

新增接口 `GET /api/regulator/evidence-chain?entId=&year=`，按时间轴返回上述节点的
「业务号 + 操作人 + 时间 + 链上交易ID + 校验状态」，监管端一页看完。

**③ 审计日志上链摘要**：每 1000 条审计日志算一次 Merkle 根上链，
使日志本身也具备防篡改能力（现在日志可被 DBA 直接改）。

## 六、【体验优化 P2】扩展性：交易品种与主体类型抽象

### 现状

`server/services/trade.js` 全程硬编码 `carbon_quota`（表名、字段 `available/frozen/bought/sold` 写死在 SQL 里）。
接入 CCER 自愿减排量时，要么复制一套 trade 逻辑，要么大改。

### 改进方案：资产层抽象

**① 统一资产账户表**

```sql
CREATE TABLE asset_account (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  ent_id BIGINT NOT NULL,
  asset_kind VARCHAR(24) NOT NULL,   -- CEA 配额 / CCER 自愿减排量 / 绿证 / 碳汇
  vintage INT,                        -- 项目年份（CCER 必需）
  project_id VARCHAR(64),             -- CCER 项目编号
  available DECIMAL(18,3), frozen DECIMAL(18,3),
  total_in DECIMAL(18,3), total_out DECIMAL(18,3),
  UNIQUE KEY uk_asset (ent_id, asset_kind, vintage, project_id)
);
```

`carbon_quota` 可作为 `asset_kind='CEA'` 的一个视图保留，向后兼容。

**② 订单表加资产维度**

```sql
ALTER TABLE trade_order ADD COLUMN asset_kind VARCHAR(24) DEFAULT 'CEA';
ALTER TABLE trade_order ADD COLUMN asset_ref VARCHAR(64) DEFAULT NULL;  -- vintage/project
```

**③ 交易主体类型抽象**：新增 `party_type`（EMITTER 控排企业 / PROJECT_OWNER 项目业主 /
INVESTOR 投资机构 / BROKER 经纪），订单与成交流程按主体类型套不同规则
（如项目业主只能卖 CCER，控排企业只能用配额履约）。

**④ 撮合规则可配置**：不同品种的撮合约束不同（CCER 有项目类型限制、绿证有地区限制），
应把"可买/可卖的资格校验"抽成策略函数，而不是写死在 trade.js。

## 七、【体验优化 P2】公众端能力偏弱

### 现状

`/api/public/*` 仅 5 个接口：dashboard、enterprises、notices（及 summary/detail）。
公众能看到大屏与名录，但看不到**核查结果**和**履约情况**——这两项恰恰是碳信息公开的重点。

### 改进方案：公示专区（脱敏）

| 公示内容 | 数据来源 | 脱敏处理 |
| --- | --- | --- |
| 核查结论公示 | `verify_report` | 公布结论（通过/不通过）、核查机构、核查日期；不公布企业商业秘密细节 |
| 配额履约公示 | `carbon_quota` + `quota_surrender` | 公布"是否按期足额清缴"、清缴比例；不公布具体金额 |
| 企业排放排名 | `emission_report` | 按行业分组、分档（A/B/C），不精确到吨 |
| 链上存证可验证性 | 链上 tx | 提供 txId 查询入口，任何人可独立验真（已具备） |

**合规提示**：公示前必须确认企业授权书是否涵盖"对外公示"（当前 4 家授权书写的是
"研究、开发、数据接入演示、碳排放核算与学术竞赛"，**未明确包含公开公示**）——
2026-10-29 版授权书已在第二条补充"如需将甲方数据用于对外公示，应经甲方另行书面确认，
书面确认可通过电子邮件、微信等电子数据形式作出"，即公示仍需逐项取得企业电子确认，
不能仅凭授权书直接公示。

## 八、优先级与实施路线

### P0（必须改，1-2 周）
1. **交易端授权链路**（trade_mandate + traderEntId 校验 + 授权页/台账页）
   —— 这是唯一的"可被直接利用"的漏洞，不修等于开放任意企业资产操作。

### P1（合规必需，2-3 周）
2. **多账号 + 岗位分级 + 双人复核**（sys_user.post + 4 个关键动作加复核字段）
3. **管理员权限收缩**（业务路由移除 ADMIN）
4. **核查/交易资质互斥**（org_qualification + 写时校验 + 每日巡检）
5. **审计统一归集 + 证据链串联接口**

### P2（体验与扩展，可迭代）
6. 企业端子角色（复用 post 机制）
7. 审计日志上链摘要
8. 资产层抽象（CCER/绿证）
9. 公众端公示专区（须先补授权范围）

### 一句话总结

**当前最危险的不是"角色边界模糊"，而是交易端的 `traderEntId()` 直接采信客户端 entId——
任何 TRADER 账号可代理任意企业下单清缴。这必须作为 P0 立即修。**
其余 6 条属于合规内控与体验优化：单账号/无复核不符合碳市场核查独立性要求，
核查与交易利益冲突缺少系统阻断，这两条在监管问询时会被直接追问，建议同步推进。
