它是**真实、可公开访问的 HTTPS 域名**，完全满足"免费服务器/域名完成线上部署"的要求。
自己花钱买 `xxx.com` 属于额外锦上添花，本次不做。

## 八、常见问题

**Q1：构建失败，日志显示 `Cannot find module 'express'`**
`package.json` 里必须有 `express` 和 `mysql2` 依赖，且仓库里不能有 `node_modules`。本项目已满足，检查是否误把 `node_modules` 提交上去了。

**Q3：页面能打开，但列表全是"暂无数据"**
数据库连上了但表是空的。回到第四章重新执行一次数据灌入。

**Q4：`/api/health` 返回 500**
如果同时报数据库错误，同 Q2。如果数据库正常，看 Render 日志里的具体报错。

**Q5：免费实例会到期吗？**
Render 免费 Web Service **不会**按月过期，只要 750 小时/月的额度够用就一直免费。
TiDB Cloud Starter 免费版同样是长期免费的（注意：TiDB "Zero" 试用实例是 30 天，**别选错**，要选 **Starter**）。

**Q6：国内访问慢怎么办？**
免费区在美国，国内直连会有延迟。这是免费方案的固有代价，不影响功能验收。如果实在需要，可考虑：

为了让项目能直接部署到云端，对代码做了一组**向后兼容**的改造（本地运行完全不受影响）：

| 文件 | 改动 | 作用 |
| --- | --- | --- |

| `server/config.js` | 端口解析改用 `num()` 兜底 | 平台把 `PORT` 注入为空串时不再退化成随机端口 |

| `server/blockchain/chain.js` | 新增 `persistTxBatch()` | 存证一次灌 900+ 笔时，把逐条 INSERT 合并为批量 INSERT，往返次数降到 1/50 |
| `server/blockchain/chain.js`<br>`server/config.js` | **时区基准统一为 UTC**（见下） | 保证「本机 MySQL」与「TiDB Cloud」反解出的区块时间戳完全一致 |
| `server/blockchain/crypto-utils.js`<br>`server/blockchain/keystore.js` | 钱包改为**确定性派生** | 同一 `ent:1` 在任何机器都得到同一对密钥，存证数据可跨环境复现 |
| `server/blockchain/chain.js` | `validateChain()` / `repairChain()` 消除 N+1 查询 | 全链校验从 155 次网络往返降为 1 次，云端耗时 **35.6 分钟 → 1.2 秒** |
| `server/routes/chain.js` | 修正区块详情 `rootMatches` 的字段名 | 原写成 `block.merkle_root`（重塑对象里叫 `merkleRoot`）导致恒为 `false` |
| `server/routes/regulator.js` | 统计分析 SQL 兼容 `only_full_group_by` | TiDB 默认开启严格模式，原语句在该模式下直接报错 |

### 10.0 三处「本地不报错、云端必出错」的真实缺陷

这三处都是本地 MySQL（宽松配置）能跑通、一上云就暴露的问题，也是本次部署最有价值的收获。

**① 时区基准不一致 → 全链 155 块全部校验失败**

见 10.1，这是最隐蔽的一处。

**② 区块详情 Merkle 比对恒为 `false`**

`server/routes/chain.js` 里 `block` 是**重塑过的驼峰对象**（字段为 `merkleRoot`），
但比对时误写成原始行的字段名 `block.merkle_root`：

```js
merkle: { rootMatches: proof.root === block.merkle_root }   // ✘ 恒为 undefined ===
```

前端「区块链浏览器 → 区块详情」会一直显示「Merkle 根与交易表比对：不一致」。
已改为 `block.merkleRoot`。

> 注意区分：`chain.js:141`、`enterprise.js`、`verifier.js` 里的 `block.merkle_root`
> 操作的是**原始数据库行**，字段名本就该是下划线，那些是**正确的**，未改动。

**③ `only_full_group_by` 严格模式 → 统计分析接口 500**

`server/routes/regulator.js` 的排行榜 SQL 中，`GROUP BY e.id` 却直接选取了
另一张表 `carbon_quota` 的非聚合列 `q.available`。TiDB 默认开启 `only_full_group_by`，
直接拒绝；本机 MySQL 8.0.29 的默认配置未开启，所以本地 50/50 全绿、云端 49/50。

修法：用 `MAX(q.available)` 包一层（`q` 已按 `ent_id + year` 唯一，取值不变），
并把 `GROUP BY` 补全为 `e.id, e.ent_name, e.industry, e.region`。

### 10.0.1 全链校验的 N+1 查询（云端部署的隐藏杀手）

原 `validateChain()` 在循环里逐块查交易：

```js
for (let i = 0; i < blocks.length; i++) {
  const [txRows] = await this.db.query('SELECT tx_id FROM chain_tx WHERE block_index = ?', [b.index]);
  ...
}
```

本地 MySQL 每次 <1 ms，完全无感。但部署后 Web 服务与数据库**跨地域**，
155 块 = 155 次网络往返，实测一次校验要跑 **35.6 分钟**，接口必然超时
（Render 免费实例的请求超时远小于这个数），用户点「系统自检」页面只能看到报错。

修法：把交易**一次性**取回，在内存里按 `block_index` 分组成 `Map`，循环内只查内存。

```js
const [allTx] = await this.db.query(
  'SELECT block_index, tx_id FROM chain_tx WHERE block_index >= ? ORDER BY block_index ASC, id ASC', [from]
);
const txByBlock = new Map();
for (const t of allTx) { /* 分组 */ }
```

实测结果：

| 环境 | 优化前 | 优化后 |
| --- | --- | --- |
| 本机 MySQL | ~100 ms | **17 ms** |
| TiDB Cloud（跨洋） | **2 137 356 ms ≈ 35.6 分钟** | **1 155 ms ≈ 1.2 秒** |

提速 **1851 倍**。`repairChain()` 存在同样的模式，也已一并修正。

### 10.1 为什么必须统一时区（这是最容易踩的坑）

区块头哈希的输入是：

```
SHA256( index | timestamp | merkleRoot | prevHash | difficulty | nonce )
```

其中 `timestamp` 是**绝对秒数**，而它在库里是以 `DATETIME`（`block_time` 列）保存的。
「DATETIME 字面量 ↔ 秒数」这一步只要两台机器解释不同，重算哈希就必然失败。

MySQL 的 `UNIX_TIMESTAMP(datetime)` 是**按会话时区**解释字面量的：

| 环境 | 服务端时区 | `'2026-01-01 10:00:00'` 被解释为 | 反解出的秒数 |
| --- | --- | --- | --- |
| 本机 MySQL | CST (+08:00) | 10:00 **+08:00** = 02:00Z | 基准 |
| TiDB Cloud | UTC (+00:00) | 10:00 **+00:00** = 10:00Z | 基准 **+28800** |

若不做处理，同一份数据在云端会整体偏移 8 小时，表现为
`✘ 校验发现 155 处异常`（每一个区块都哈希不匹配）。

**本项目采用的解法（两步缺一不可）**：

1. **服务端侧**：连接建立后立即执行 `SET time_zone = '+00:00'`（`chain.js` 的 `syncTimeZone()`，在 `init()` / `validateChain()` / `repairChain()` 入口都会调用）。
2. **写入侧**：不再把 JS `Date` 对象交给驱动（那会触发本地时区换算），而是用 `Blockchain.utcDateString(sec)` 直接格式化成 UTC 字面量字符串。

两者配对后，`utcDateString(ts)` 写进去的字符串，被 `UNIX_TIMESTAMP()` 读出来必然还原成同一个 `ts`，与服务器时区无关。

> 校验方法：`SELECT block_time, UNIX_TIMESTAMP(block_time) AS ts FROM chain_block LIMIT 1;`
> 再用 `Blockchain.calcHash()` 复算 `block_hash` 应完全相等。

#### ⚠ 连带影响：SQL 转储也必须重新导出

`db/02_seed_data.sql` 与 `db/03_full_backup.sql` 里保存的是 `block_time` 的**字面量**。
字面量的格式由**写它时的时区约定**决定，因此时区改造后，**旧转储会失效**：

| 转储生成时机 | `block_time` 字面量 | 用新代码读取 |
| --- | --- | --- |
| 改造前（旧约定） | CST 归一化，如 `2026-09-16 21:05:27` | ✘ 反解出的秒数差 28800，链校验全错 |
| 改造后（UTC 基准） | UTC，如 `2026-10-06 05:18:41` | ✅ 与原值逐位一致 |

**结论：只要改动了时区基准，就必须重跑一次 `npm run export-sql` 重新导出转储。**
本次已按新约定重新导出，并**实测验证**过：

```
新建临时库 → 导入 03_full_backup.sql → 用新代码读取路径装载 → 全链校验
结果：16 张表 / 155 区块 / 911 存证，valid = true，异常 0
```

### 10.2 为什么钱包要改成确定性派生

初始化脚本会在本机跑一遍、在云端再跑一遍。如果钱包是随机生成的，两端的
**公钥、钱包地址、ECDSA 签名**都会不同，那么：

- 同一份 SQL 备份无法在两端通用；
- 链下比对（`dbMatchesSnapshot`、验签）在换环境后全部失效。

改成 `SHA256('carbonchain-hub/keystore/v1|' + label)` → 取模曲线阶 → PKCS#8 封装后，
`ent:1`、`verifier:3`、`regulator:system` 这些标签在任何机器上都代表同一个身份，
真正做到了「一套脚本，两端可复现」。

#### ⚠ 踩坑记录：改了派生算法，旧 keystore.json 会把确定性「吃掉」

改造中真实踩过一次坑：**代码换成确定性派生了，但数据里还是随机密钥。**

原因是 `keystore.js` 的 `walletFor(label)` 逻辑是「标签不存在才生成」：

```js
if (!this.cache[label]) this.cache[label] = cu.generateWallet(label);   // 旧实现
```

只要 `server/keystore.json` 已经存在（本机调试时早就生成过 111 个**随机**钱包），
重新跑 `init-db` 时它**一条都不会重新生成**，确定性函数根本没被调用过。
后果是：本机 keystore / 数据库里的地址与实时派生值**全部对不上**：

| 标签 | 旧 keystore 中的地址 | 确定性派生地址 | 一致 |
| --- | --- | --- | --- |
| `ent:1` | `0x0b9586…877f` | `0xc8adfc…5611` | ✘ |
| `verifier:1` | `0x2ffaf3…5053` | `0xacbfe9…efe9` | ✘ |
| `regulator:system` | `0x44b53d…c598` | `0xd766aa…cfac` | ✘ |

而 Render 上**没有 `keystore.json`**，服务会用确定性函数现生成一套新密钥，
于是「线上签的存证」与「数据库里存的公钥」对不上 —— 验签会失败。这是必须先修掉的部署阻断点。

**修复**：删掉旧的 `server/keystore.json` 后重跑初始化，让 111 个钱包全部走确定性路径。

```
rm server/keystore.json
node server/scripts/init-db.js        # 全部 111 个钱包确定性重生成
→ 链高度=154  总区块=155  链上交易=911  ✅
```

验证（逐条比对 keystore 与实时派生）：`一致: 111   不一致: 0`。

> **教训**：凡是「生成算法」发生变更，务必要清理由旧算法产生的**持久化产物**
> （keystore、缓存、转储），否则新算法会被静默绕过 —— 而且表面上一切正常，
> 只有跨环境比对时才会暴露。
