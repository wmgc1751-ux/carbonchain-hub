# 补充企业主体实现报告（方案 A）

日期：2026-10-29
范围：`碳链通平台/CarbonChainHub`
决策依据：用户选择**方案 A** —— 企业主体真实、业务流水演示、两者界面分开标识

---

## 一、要解决的问题

平台有 8 个功能页面后端完整、但数据库里一行数据都没有，打开就是空白：

| 功能页面 | 空表 | 缺失原因 |
| --- | --- | --- |
| CBAM 证书 | `cbam_declaration`、`cbam_certificate` | 4 家真实企业都是垃圾焚烧，行业不在 CBAM 六大类 |
| 碳信用与抵销 | `credit_asset`、`credit_offset` | `asset_kind_dict` 要求 CCER/GEC/FOREST 卖方为 `PROJECT_OWNER`，4 家都是 `EMITTER` |
| 绿电溯源 | `green_power_match`、`green_cert` | 缺能耗数据，且无绿电项目业主 |
| 活动数据台账 | `activity_data` | 从未生成 |
| 核算批次 | `calc_batch` | 方法学未登记「垃圾焚烧发电」行业 |
| 零知识承诺 | `zk_commitment` | 依赖核算批次，批次为空 |
| 核算不确定度 | `uncertainty_posterior` | 同上 |
| 监管预警 | `alert_record` | 从未生成 |

根因不是"没写功能"，而是**这 4 家企业的行业类型支撑不起这些功能**：
CBAM 要钢铁/铝/水泥/化肥/电力/氢，碳信用要项目业主，
而平台只有 4 家垃圾焚烧厂。

## 三、数据注入与可辨识性

这是本次最核心的设计。方案 A 的要害是"企业真实、业务演示、**两者界面分开标识**"，
所以可辨识性不是文案问题，是数据模型问题。

### 三处叠加的标识（缺一不可）

| 层级 | 机制 | 效果 |
| --- | --- | --- |
| 数据库 | `data_source='DEMO_SUPPLEMENT'` | 与真实派生的 `DERIVED_FROM_CEMS` 在 SQL 层就能分开 |
| 血缘 | 演示数据**没有** `derivation_log` 记录 | "能否回溯到真实输入"本身就是真假分界线 |
| 单据内 | `remark` 首行写【演示数据】 | 打开单据就能看到 |

**为什么"无血缘"是刻意设计而非瑕疵：**
真实企业的 32 张上报单每张都有血缘，能一路回溯到 CEMS 批次号和官方统计表。
演示数据没有血缘——这不是偷懒，是让 `derivation_log` 表本身成为真假判据。
审计脚本 I1 只检查 `DERIVED_FROM_CEMS`，因此演示数据不会污染真实侧断言。

### 资产侧同样处理

- `credit_asset.registry = 'DEMO'`（真实应为 `CCER登记簿` / `中国绿证`）
- 编号前缀 `DEMO-`：`DEMO-CCER-2024-xxxx`、`DEMO-GEC-2024-0001`
- 绿证 `issuer` 写"国家可再生能源信息管理中心（演示）"

### 量级取舍

初版按行业大厂规模建（钢铁 120 万吨、热电 300 万 MWh），
结果演示数据占总量 **87%**，公示大屏的"年度排放"变成 978 万 t，
真实数据的 144 万 t 反而成了零头。

这不是数值算错，是**比例失衡**：补充件的体量压过了主体。

调整为中型规模（钢铁 60 万吨、热电 100 万 MWh）后，演示数据占 73%。
这个比例仍是人为选择，所以在 remark 和本文档都写明，不假装它是自然形成的。

## 四、顺带修出的真实缺陷

### 缺陷 1：方法学缺「垃圾焚烧发电」，整条核算链是断的（严重）

`POST /api/mrv/calc` 对 4 家真实企业一律返回：

```
行业「垃圾焚烧发电」未在方法学中登记排放源清单，无法核算
```

意味着平台接入的真实企业**根本无法走核算流程**——活动数据、核算批次、
零知识承诺、不确定度、CBAM 全部卡在这一步。

补上行业方法学，并且是按真实口径写的，不是照抄燃煤电厂：

```js
垃圾焚烧发电: {
  combustion: ['DIESEL'],        // 只列点火助燃柴油
  process: ['MSW_FOSSIL'],       // 主排放源：生活垃圾化石碳组分
  indirect: [],                  // ← 自发电，无净购入电力
}
```

三个关键判断：

- **只算化石碳**：生活垃圾中塑料/橡胶等化石基组分的 CO₂ 计入，
  厨余/纸/木材等生物质组分按碳中和处理。这是本平台用
  0.390 tCO₂/t 而非垃圾总含碳量（约 0.7–0.9 tC/t）的原因。
  误用总含碳量会把排放高估一倍以上。
- **无间接排放**：垃圾焚烧厂是自发电企业，厂用电来自本厂机组，
  不存在"净购入电力"。若照搬燃煤电厂清单把 `POWER` 列进来，
  引擎会一直报"应核算电力但未提供活动数据"，而企业根本拿不出这数据。
- **因子 0.3705 = 0.390 × 0.95**，与 `emission_calc` 表的算法完全一致，
  保证"方法学核算"与"活动水平法派生"两条路径得到同一个数。

修复后核算结果：2024 年 49,961.67 t、2025 年 51,591.93 t，gapCount=0。

### 缺陷 2：零知识页面断言「尚未接入真实企业 CEMS」——一句可被一眼证伪的错话

`/api/zk/data-truth` 判断依据是 `cems_reading`（平台自举的模拟表），
漏掉了 `cems_cn_hourly`（河北省真实数据）。结果库里躺着 13 万条真实实测、
4 家企业、184 个已上链批次，这个页面却在说"尚未接入"。

而且这个错话恰好出现在**"数据真实性声明"**这个最不能说不实的页面上。

修正为按 `cems_cn_hourly` 实际行数判断，并把关键数字一并返回，让声明本身可被核验：

```
已接入 4 家真实控排企业的 134,400 条 CEMS 小时实测数据（河北省污染源自动监控
信息公开系统，184 批次全部上链）。其中 32 张上报单由真实 CEMS + 官方活动水平
派生、可逐项回溯；16 张为补充主体的演示数据，标注 DEMO_SUPPLEMENT、无血缘、不可回溯。
```

### 缺陷 3：企业工作台"0 tCO₂e"掩盖了草稿数据

`emissionYtd` 只算非草稿（口径正确），但新建企业的演示数据全是 DRAFT，
工作台显示"2026 年度累计排放 0"，用户以为数据没进来。

补 `draftCount` / `draftEmission` 两个字段，界面显示
"另有 4 张草稿 1,170,000 t 未提交"——既保留了"已申报 0"的准确口径，
又解释了这个 0 是怎么来的。

### 缺陷 4：审计脚本口径未跟上数据分层

补充主体引入后，`derivation-audit.cjs` 的 I2 和 I5 从 8/8 掉到 6/8。
查下来不是数据错了，是**审计口径没跟上**：

- I2 断言"所有上报单 data_source 必须为 DERIVED_FROM_CEMS"，
  把演示数据误报为违规
- I5 拿演示数据与官方基数比，而演示量级本就来自行业参数，不可能对齐

修正为分层审：真实派生侧查血缘/可回溯/闭合，
演示侧查"不可回溯 + 已标注 + 不冒充"。
修好后 10/10（比原来多 2 项分层断言）。

## 六、能证明什么、不能证明什么

### 能证明

1. 8 个原先空置的功能页面现在都有可展示的数据
2. 真实 / 派生 / 演示三类数据在数据库层、血缘层、单据层三重可辨识
3. 演示数据不会污染真实数据的审计断言（分层审计 10/10）
4. 垃圾焚烧行业方法学补齐后，真实企业核算链从断掉变为完整（gapCount=0）

### 不能证明（必须如实说明）

1. **不能证明这 3 家新增主体的业务数据是真实的。** 它们是演示数据。
   石钢的年产钢、华电的供电煤耗、张北的 CCER 减排量，全部是行业量级参数，
   不是任何一家企业的实际台账。
2. **不能证明华电与张北风电是已核验的工商主体。** 前者信用代码待补，
   后者本身就不是一家具体企业（是项目业主的聚合指代）。
3. **不能证明 CCER / 绿证经过了真实核发。** 编号带 `DEMO-` 前缀，
   登记簿写 `DEMO`，未在国家登记系统核发。
4. **不能证明石钢的 CBAM 申报包可用于实际申报。** 其排放数据来自演示参数，
   EU 缺省值仅作量级对照，不构成申报依据。
5. **不能证明补充主体能走完履约闭环。** 它们没有配额分配、没有核查任务、
   没有清缴记录——这些流程仍只对 4 家真实企业跑通过。

## 八、一句话总结

新增 3 家主体（1 家信用代码可核验、2 家明确标注待核验），
让 8 个空置功能页面从"打开是空白"变成"有数据可看、有流程可走"。

真正有价值的不是这些演示数据，而是**三类数据在库层面就分得开**：
真实派生的 32 张有血缘可回溯，演示的 16 张无血缘且单据内标注，
审计脚本对两侧分别断言、10 项全过。

过程中还修出一个更严重的问题：平台接入的 4 家真实企业
**原本根本无法核算**（方法学里没有"垃圾焚烧发电"行业），
补齐后核算链才真正打通。
