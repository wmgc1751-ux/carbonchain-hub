# 基于区块链的企业碳排放数据存证与碳配额交易平台设计与实现

**Design and Implementation of a Blockchain-Based Platform for Enterprise Carbon Emission Attestation and Allowance Trading**

---

## 摘要

全国碳排放权交易市场的地基是数据：企业申报的排放量决定配额缺口，配额缺口决定真实的交易与履约。然而碳排放数据天然存在"由被监管者自己申报、事后易于修改、责任难以界定"的治理难题，传统中心化信息系统无法为数据提供"可被第三方独立验证"的可信证明。本文设计并实现了一个面向四类主体的碳数据存证与配额交易平台——**碳链通 CarbonChain Hub**。系统采用"链下关系库承载业务查询、链上哈希链承载可信锚点"的双层数据架构：后端基于 Node.js + Express 自研联盟链内核，实现 SHA-256 哈希链、前导零工作量证明、Merkle 树及其存在性证明、secp256k1 ECDSA 数字签名与钱包地址派生，不依赖任何区块链第三方库；前端基于 Vue 3 与 ECharts 构建免构建单页应用，覆盖企业端、第三方核查机构端、生态环境主管部门端与社会公众端四种角色视图。关键业务动作（排放上报、核查报告签发、配额分配、交易成交）均以发起方私钥签名后上链存证，并支持任意第三方在不下载全链的前提下，仅凭交易哈希与 Merkle 路径复算区块头根哈希完成存在性验证。系统通过 49 条后端接口自检用例、27 条路由的无头浏览器渲染巡检与 5 项端到端交互回归完成验证，全部通过；全链完整性校验（162 个区块、918 笔存证）耗时 31.4 ms（P95 37 ms），篡改实验表明篡改单块将导致其后 150 个区块哈希全部改变、重做工作量证明需 10.6 秒，量化地体现了区块链"篡改可察觉、成本极高"的安全属性。

**关键词**：区块链；碳排放数据；哈希链；工作量证明；Merkle 树；数字签名；碳配额交易；可信存证

## 1 引言

### 1.1 研究背景

据公开报道，全国碳排放权交易市场已覆盖发电、钢铁、建材、有色、石化、化工、造纸、航空等八个高排放行业，年覆盖二氧化碳排放量约 50 亿吨，是全球覆盖排放量最大的碳市场。市场的运行逻辑是"配额—排放—交易—履约"的闭环：主管部门向控排企业免费分配或竞价发放配额，企业按期申报实际排放量，排放量超过配额的企业需在市场上购买配额以完成履约，配额盈余的企业则可出售获取收益。

这一闭环的安全基础是**排放数据的可信性**。而碳排放数据的计量与申报具有三个与生俱来的特征：

1. **自申报性**：排放量由企业自行核算并填报，企业既是数据的生产者，又是数据真实性的最大利益相关方；
2. **可修改性**：在传统信息系统中，填报记录本质上只是数据库中的若干行，拥有写权限即可修改，而修改后无法留下可被外部验证的痕迹；
3. **责任模糊性**：第三方核查机构出具报告后，报告在中间环节仍可能被调整，企业与机构之间容易出现"数据是谁改的"之争。

此外，社会公众对碳市场运行情况几乎无从核验，"谁排了多少、谁买了多少"处于黑箱状态，不利于形成社会监督。

### 1.2 区块链的适用性分析

区块链并非"所有场景都需要"的技术。理解其适用边界，是本项目选题的第一道功课。区块链真正不可替代的能力是：**在互不信任的参与方之间，提供一个不可篡改、可公开追溯、可独立验证的公共账本**。将其与本课题对齐：

| 业务痛点 | 区块链提供的解决手段 | 传统方案的不足 |
| --- | --- | --- |
| 数据来源不可抵赖 | 企业私钥对数据签名，链上留公钥可验证 | 账号密码可共享、可代填，无法证明"是企业本人提交" |
| 签发后不可篡改 | 报告摘要上链，任何改动导致链下数据与链上哈希不一致 | 数据库行可被直接改写，日志也可被清空 |
| 配额分配全程留痕 | 分配动作由监管节点签名存证，形成时间戳序列 | 公文流转与系统操作记录分离，难以追溯 |
| 账实相符、可审计 | 成交即存证，链上时间戳作为清算时点 | 撮合结果与账务流水缺少密码学绑定 |
| 公示可核验 | 公开链上区块与交易，提供 Merkle 存在性证明 | 公示页面的数据来源无法验证 |

因此，本项目把区块链严格限定在"**存证与验证**"这一层，而不去解决它并不擅长的"高频业务查询与统计"——后者交由链下关系库处理。这种"链上锚点 + 链下业务"的分工，是本文的核心设计取舍。

### 1.3 本文主要工作

1. **设计并实现了四端协同的业务系统**：企业端、第三方核查机构端、生态环境主管部门端、社会公众端，共 27 个功能页面，覆盖排放上报、自动派单、核查签发、配额账户、撮合交易、市场监控、风险预警、统计分析、链上核验、操作留痕、通知公告等完整业务链。
2. **自研了一套可讲清原理的联盟链内核**：SHA-256 哈希链 + 前导零工作量证明 + Merkle 树与存在性证明 + secp256k1 ECDSA 签名 + 钱包地址派生 + 私钥离线托管，全部基于 Node.js 内置 `crypto` 实现，不引入任何区块链第三方库，代码可逐行解释。
3. **提出了面向碳数据的"四道关"全链完整性校验方法**：内容哈希关、前驱指针关、难度关、Merkle 根关，并实现了可视化的篡改—察觉—修复实验台。
4. **建立了可复现的自动化验证体系**：49 条后端接口自检用例、基于 Chrome DevTools Protocol 的无头浏览器路由巡检（27 条路由 + 5 项交互，同时采集 DOM 体量、表格行数、图表实例数、未解析组件与控制台异常）、10 个接口的性能采样，以及证据自动汇总页面。

## 2 相关技术

### 2.1 哈希链与区块链

区块链的核心数据结构是一条由密码学哈希函数串联的链。设第 $i$ 个区块的内容为 $C_i$（包含区块高度、前一区块哈希、Merkle 根、随机数、难度、时间戳与交易集合指纹），则

$$H_i = \mathrm{SHA256}(C_i),\qquad H_i \text{ 作为第 } i+1 \text{ 区块内容的一部分}$$

由于 SHA-256 具有**抗原像性**（无法由哈希反推内容）与**抗第二原像性 / 强抗碰撞性**（无法找到两个不同内容产生同一哈希），任意区块内容被修改都必然导致 $H_i$ 改变，进而导致其后所有区块的哈希失效。这使得篡改不可能"只改一处"。

### 2.2 工作量证明（PoW）

仅靠哈希链可以"察觉"篡改，但攻击者可以重算被篡改区块之后的全部哈希来"修复"链条。工作量证明通过人为制造计算成本来对抗这种重算：要求区块哈希满足特定条件（本文采用**前导零个数 ≥ difficulty**），寻找满足条件的 `nonce` 只能通过穷举，平均需要 $16^{\text{difficulty}}$ 次哈希运算。本文难度取 4，实测平均出块耗时 76 ms，最大 469 ms，便于在演示中直观展示"计算成本随难度指数上升"。

同时，PoW 使篡改的代价可被量化：一旦某个区块被改动，其后所有区块都需重新寻找 nonce。

### 2.3 Merkle 树与存在性证明

Merkle 树将区块内 $n$ 笔交易两两配对哈希、逐层归并，最终得到唯一的 Merkle 根写入区块头。其价值在于**只要持有根哈希与一条长度为 $O(\log n)$ 的路径，即可验证某笔交易确实属于该区块**，无需获取区块全部交易。本文的路径元素表示为 `{position: 'left'|'right', hash}`，验证算法为：从交易哈希出发，按路径顺序与兄弟哈希拼接后取 SHA-256，最终结果应等于区块头的 Merkle 根。当区块仅含一笔交易时，根即为该交易哈希（单叶场景），系统对此给出明确提示，避免与"数据缺失"混淆。

### 2.4 数字签名与身份

本文采用 secp256k1 曲线上的 ECDSA 签名（Node 内置 `crypto` 支持），用于回答"这份数据是谁签的"。与哈希函数提供的"完整性"相比，签名额外提供了**不可否认性**：只有私钥持有者能生成有效签名。系统进一步将公钥经 `SHA-256 → RIPEMD-160` 后派生为钱包地址，形成"角色—地址—签名"的一一映射：

- 企业签名 ⇒ 该排放数据确由该企业提交；
- 核查机构签名 ⇒ 该结论确由该机构签发；
- 监管节点签名 ⇒ 该配额分配确由主管部门作出；
- 买卖双方签名 ⇒ 该成交价量与链上时间戳一致。

私钥以加密 keystore 形式离线托管，业务数据库只保存公钥与地址，从而保证即使业务库泄露也无法伪造签名。

### 2.5 系统实现技术栈

后端采用 Node.js 22 + Express 4，使用 `mysql2` 连接池访问 MySQL 8.0；认证采用基于 `crypto.createHmac` 自实现的 JWT（HS256）；前端采用 Vue 3.4 与 ECharts 5.5，依赖全部本地化、无构建步骤，由后端同端口托管静态资源。整个系统生产依赖仅 `express` 与 `mysql2` 两个包。

## 3 系统设计

### 3.1 总体架构

系统采用四层架构：

```
展示层    Vue 3 单页应用（企业端 7 页 / 核查端 5 页 / 监管端 9 页 / 公众端 6 页）
   │ REST + JWT
接口层    60 个 REST 接口（auth / enterprise / verifier / regulator / chain / public）
   │
服务层    上链存证服务 anchor.js　碳配额撮合引擎 trade.js
   │
链内核    crypto-utils（哈希/Merkle/ECDSA/地址派生）· chain（哈希链/PoW/交易池/全链校验）· keystore（私钥托管）
   │
数据层    MySQL 8.0：链下业务表 14 张 + 链上存证表 2 张（chain_block / chain_tx）
```

### 3.2 角色与权限设计

系统以单一账号体系加 `role` 字段实现四端分离，登录后由前端路由守卫强制限定在角色前缀内（企业 `/ent`、核查 `/ver`、监管 `/reg`），越权访问自动提示并返回本端工作台。这种"一套认证、四套视图、四类数据边界"的设计，既简化了账号维护，又能在链上通过不同签名主体区分责任。

### 3.3 数据模型

数据库共 16 张表，分为三组：

- **主体表**：`sys_user`（114）、`enterprise`（60）、`verifier_org`（50）；
- **业务表**：`emission_report`（360）、`emission_item`（1278）、`verify_task`（340）、`verify_report`（273）、`carbon_quota`（120）、`quota_allocation`（148）、`trade_order`（270）、`trade_deal`（90）、`alert_record`（72）、`notice`（60）、`audit_log`（250）；
- **链上存证表**：`chain_block`（162）、`chain_tx`（918）。

业务表通过 `chain_block_index` / `chain_tx_id` 反向指向链上存证，形成"链下可查、链上可证"的双层结构。所有表均满足课程"每表 50 条以上假数据"的要求，且链上两表的数据由初始化脚本真实执行 PoW 出块产生，而非伪造。

### 3.4 链上存证模型

| 层次 | 字段 |
| --- | --- |
| 区块 | 高度、区块哈希、前驱哈希、Merkle 根、nonce、难度、交易数、字节数、出块耗时、出块节点、出块时间 |
| 交易 | 交易哈希、类型（五类业务）、业务单号、发起/接收地址、载荷哈希、签名、公钥、所属区块、nonce、手续费、状态 |

### 3.5 业务流程设计

**流程一：排放数据上报与存证。** 企业按"年度 + 季度"填报能源消耗明细，系统按排放因子自动折算范围一（直接排放）与范围二（间接排放），并计算综合能耗、强度与同比。提交时使用企业私钥对规范化序列化的载荷签名，生成存证交易入池、出块，随后回写业务表的区块高度与交易号，并按规则自动派单至第三方核查机构。

**流程二：核查与报告签发。** 核查机构受理任务后核对数据，出具"通过 / 有条件通过 / 不通过"结论；报告签发即以上链方式固化，形成机构签名的不可抵赖记录。

**流程三：配额分配与交易。** 监管端依据行业基准与产量核定年度配额并签名下发；企业端在配额账户中查看可用余额与履约缺口，通过"价格优先、时间优先"的连续撮合市场挂单交易，支持部分成交与撤单，成交即存证。

**流程四：监管与公示。** 监管端基于全市场数据生成五类风险预警（配额超限、数据异常、漏报、价格异动、链上风险）并进行受理与闭环处置；公众端可免登录访问公示大屏与区块链浏览器，独立核验任意存证。

## 4 关键实现

### 4.1 上链存证服务

存证服务将业务动作抽象为统一管线：**业务落库 → 组装载荷 → 规范化序列化 → 哈希 → 私钥签名 → 入池 → 出块 → 回写锚点**。其中"规范化序列化"（键排序、去除空白）保证了同一业务数据在任何环境下产生相同的载荷哈希，是链下数据与链上存证能够逐字节比对的前提。

链下与链上的四种一致性由核验接口一次性给出：签名有效性、载荷哈希是否一致、链下当前数据是否与存证快照一致（可发现"上链后又改了库"）、Merkle 根是否一致，并在前端以结论读数块 + Merkle 路径的形式可视化。

### 4.2 碳配额撮合引擎

撮合引擎维护买卖两侧按价格优先、时间优先排序的委托队列。新挂单进入后立即尝试与对手方最优价撮合，支持部分成交（订单状态置为 `PARTIAL`）与全部成交（`FILLED`）；未成交部分留在队列中，可随时撤单（`CANCELLED`）。每笔成交生成一条 `TRADE_DEAL` 存证交易上链，使"成交价量—链上时间戳—账务流水"三者密码学绑定。

### 4.3 防篡改与全链完整性校验

全链校验按四道关依次执行，任一道失败即返回异常清单（区块高度 + 原因 + 期望值 / 实际值）：

1. **内容哈希关**：逐块重算区块哈希并与库中记录比对；
2. **前驱指针关**：校验每块的前驱哈希等于前一区块哈希，断链立即暴露；
3. **难度关**：校验区块哈希前导零个数达到难度要求，防止篡改者绕过 PoW；
4. **Merkle 关**：复算每块交易集的 Merkle 根并与区块头比对。

为便于演示与教学，系统提供"篡改—察觉—修复"实验台。实测：篡改区块 #10 后校验立即返回 `valid=false`、异常数 2；执行修复需重做 150 个区块的工作量证明，总耗时 10,574 ms，且被篡改区块之后的**全部区块哈希发生改变**——这正是区块链安全性的直观量化。

### 4.4 前端公示与区块链浏览器

公众端无需登录即可访问数据公示大屏、区块链浏览器、公告与碳价行情。浏览器提供区块列表与详情、交易列表与详情、地址视图、交易池与全链校验入口；交易详情页同时展示验签结论、载荷哈希、区块信息与 Merkle 证明路径，使"可独立验证"成为普通用户可操作的界面功能，而非停留在设计文档中的承诺。

### 4.5 开发过程中发现并修复的典型缺陷

工程实现中暴露了两个具有代表性的问题，对理解所用框架的行为有普遍意义，特此记录：

1. **渲染函数中的字符串标签不查组件注册表。** 在 Vue 3 中，渲染函数 `h('x-card')` 的字符串标签会被当作原生元素处理，而**不会**查询全局组件注册表。这一行为导致页面骨架正常、内容区空白且控制台无任何报错（生产版 Vue 不输出解析失败警告），极具迷惑性。解决方案是在内核层提供组件名解析版 `h`：当标签命中组件注册表时改传组件对象，从而在不改动数百处视图代码的前提下修复。
2. **路由参数未注入视图组件。** 详情类页面依赖 `props.txId` 等参数发起请求，而应用外壳未将路由参数传入，导致请求打到 `/chain/tx/undefined`。修复方式是按路由路径注入 props，并以完整路径作为组件 `key`，保证在"区块 A → 区块 B"时组件重新挂载、数据不串页。

### 5.2 功能测试

**后端接口自检**：以四种角色登录，遍历 60 个接口中的核心路径并断言 HTTP 状态与业务返回码，共 **49 条用例，通过 49 条，失败 0 条**（含越权访问、重复上报、非法参数等异常分支）。

**前端路由渲染巡检**：采用无头浏览器逐页真实渲染，每页回读 DOM 文本量、表格与行数、图表实例数、未解析组件与控制台异常。结果：**27 条路由全部通过，控制台异常 0，未解析组件 0**。

**端到端交互回归**：5 项关键交互全部通过——表单登录并进入工作台、上报列表打开详情弹窗、浏览器点入区块详情、监管预警打开处置弹窗、企业端打开链上核验弹窗（弹窗内呈现 4 项通过结论与 Merkle 证明路径）。

### 5.4 链上数据与安全性验证

| 指标 | 实测值 |
| --- | --- |
| 链高度 / 区块总数 | 161 / 162 |
| 链上存证交易 | 918（排放上报 343、核查报告 273、配额分配 152、交易成交 90、企业备案 60） |
| 当前难度 | 4（前导零） |
| 单区块出块耗时 | 平均 76 ms |
| 平均每区块打包交易 | 5.8 笔（最多 8 笔） |
| 全链完整性校验 | `valid=true`，异常数 0 |

**篡改实验**：篡改区块 #10 内容后，校验立即报告 `valid=false` 且异常数为 2，首条异常明确指出"区块 #10 内容哈希与记录不符，期望 `78230a4569ce0b9a…`，实际 `0000833dd2fee572…`"；执行修复需重做 150 个区块的工作量证明，耗时 10,574 ms，修复后恢复 `valid=true`。该实验从两个层面说明区块链的安全属性：其一，篡改**必然被察觉**（哈希链的连锁效应）；其二，篡改**代价随难度指数增长**（PoW 的计算壁垒）。

**越权与重复提交测试**：企业身份访问监管接口被拒绝并提示返回本端工作台；同一企业同一"年度 + 季度"重复提交上报被业务规则拦截（返回 400 与明确提示）。这说明系统在应用层的权限边界与业务幂等约束有效。

### 5.5 结果讨论

1. **"链上锚点 + 链下业务"的分工被验证是可行的**：链只承担存证与验证职责，业务查询与统计仍走关系库，因而本系统在保持不可篡改特性的同时，性能与传统 Web 系统没有量级差异。
2. **可验证性必须下沉到界面**：区块链提供的是"可验证的能力"，若第三方无法方便地执行验证，则可信性无法被感知。本系统将验签、载荷比对、Merkle 路径复算做成了一次点击即可查看的弹窗，这是"技术可信"转化为"用户可感"的关键环节。
3. **PoW 在教学演示中应选择低难度**：难度 4 时平均出块 76 ms，既能真实体现"需要穷举 nonce"的机制，又不会让演示等待过久；而修复实验的 10.6 秒耗时可用来向观众外推真实公链的指数级成本。
4. **本次开发的最大工程风险来自框架行为细节而非链逻辑**：链内核的正确性可通过全链校验自证，而前端"渲染函数字符串标签不查组件注册表"这类静默失效的问题，恰恰因为不报错而最难定位。这提示在开发中应建立**面向渲染结果的自动化巡检**（本文的 CDP 巡检脚本正是在踩坑后补建的）。

## 6 结论与展望

本文围绕"碳排放数据的可信治理"这一真实问题，设计并实现了一个基于区块链的四端协同平台。系统的核心贡献在于：以"链上锚点 + 链下业务"的双层数据架构，把区块链严格限定在它不可替代的存证与验证环节；以自研的哈希链、PoW、Merkle 树与 ECDSA 签名内核，提供了一个原理可解释、代码可审计、无需第三方库的可信层；以四端签名主体分离的存证模型，使链上能够精确回答"是谁在什么时候签了什么"；并通过 49 条后端用例、27 条路由的无头浏览器巡检与 5 项交互回归，建立了可一键复现的验证体系。

系统仍存在若干局限：目前为单节点链，去中心化体现在数据结构与签名机制而非网络共识；私钥由服务端托管，尚未实现企业端本地密钥生成；交易池为内存实现，进程重启后未打包交易会丢失；缺少针对链内核的单元测试。后续工作将从四个方向推进：引入多节点 P2P 广播与最长链选择以形成真实的多方共识；将密钥生成下沉到浏览器端使私钥不出端；交易池落库并支持重启恢复；以及引入单元测试框架对 Merkle 计算、PoW 校验、签名验签等核心函数做穷尽覆盖。
