## 二、意见① 信任模型硬伤

> **院审原文**：链上锚点与链下明文同库，DBA 一条 UPDATE 即可同时篡改，与"管理员无法事后篡改"声明证据不对等。
> **建议**：链库与业务库物理分离，篡改实验增设"同库同改"攻击用例。

### 问题定性

上一轮的整改只做到"同实例、另一个 schema"（L1）。这在现场经不起推敲：同一个 MySQL 实例里，DBA 一个会话就能执行

```sql
UPDATE carbon_chain.emission_report   SET total_emission = ... ;
UPDATE carbon_chain_ledger.chain_tx   SET payload_json   = ... ;
```

两条语句、一次提交。"一条 UPDATE"只是变成了"两条"，而声明强度没有变化。

### 整改内容

**1) 账本库搬到独立 MySQL 实例（L3）**

- 新增第二实例配置 `D:/MySQL/mysql-8.0.29-winx64/my-ledger.ini`（端口 3307，独立数据目录、独立账号 `cc_ledger`）。
- 新增迁移工具 `tools/split-ledger-instance.mjs`：
  - 默认 dry-run，`--execute` 才落地，执行前先把源库整表导出为 JSON 备份；
  - 迁完逐表校验行数，并**比对链顶哈希**（同高度必须同 `block_hash`）——证明搬的是同一份链，不是"看起来像"。
  - 实测结果：`chain_block 260→260`、`chain_tx 1007→1007`、链顶 `#259 7659015b…` 两侧一致。
- 迁移完成后**删除了业务库中的 5 张同名视图**。跨实例视图本就不可用，留着只会让代码继续依赖"反正同实例"的假象。

**2) 代码层的跨实例改造（真正的难点）**

账本搬到独立实例后，原先所有"靠同实例跨库视图"的查询会全部失效。已逐处改为显式账本通道：

- `server/db.js` 新增 `ledgerOne / ledgerValue / ledgerPaginate / separationFacts`。
- 改造点：`routes/chain.js`、`enterprise.js`、`verifier.js`、`regulator.js`、`public.js`、`evidence.js`、`services/consortium.js`、`carbonCopilot.js`、`infra.js`。
- **两处跨库 JOIN 拆成应用侧合并**（跨实例下不可能成立）：
  - `routes/chain.js` 的 `enterprise LEFT JOIN chain_tx` → 两段查询后内存归并；
  - `routes/enterprise.js` 的 `chain_tx JOIN emission_report` → 先取本企业 txId 清单，再向账本库计数。
- `server/scripts/start-prod.js` 的启动自检原先会去业务库找 `chain_node`——L3 下必然找不到，**会误判"旧版结构"并触发整库重建**。已改为两侧分别探测。这是一个会导致丢数据的隐患，顺手修掉了。

**3) 隔离强度分级，不再使用模糊表述**

把"分离"拆成四档，写进接口与页面：

| 档 | 形态 | 拦得住"一条连接同改"？ |
| --- | --- | --- |
| L0 | 同库同表 | 否 |
| L1 | 同实例不同库 | 否（DBA 同会话两条 UPDATE 仍可同改） |
| L2 | 不同实例同账号 | 是（账号泄露则两侧都能动） |
| L3 | 不同实例不同账号 | 是（业务侧凭据任何情况下都够不到账本） |

**4) 新增「DBA 凭据越权同改」攻击用例**

这是最贴近院审原话的复现：用**业务侧最高权限账号**的原始连接，尝试一条语句改两边。判定要点不是"是否报错"，而是**在哪一层被拦住**：

```
✔ DBA 凭据越权同改   预期 SPLIT_AT_CONNECTION   实际 SPLIT_AT_CONNECTION [ER_BAD_DB_ERROR]
  改业务明文成功、改账本被拒（连接层：库不在该实例上）
```

注意对照组：业务库明文那一步**必须成功**，否则说明业务账号本身有问题，演练结论就不成立——不能靠"业务库也改不动"来冒充安全。

### 证据与复现

```bash
node tools/split-ledger-instance.mjs          # 预演搬迁计划（只读）
node tools/attack-same-db.mjs                 # 8 组攻击演练，末行给出隔离强度
curl http://127.0.0.1:8300/api/chain/trust-model   # 页面数据源，实时查库
```

页面入口：平台 → 科研验证中心 → **信任模型**（① 链库物理分离），以及小程序 → **链路** → 信任模型卡片。

> **本轮踩到并修掉的坑**：`separated` 一开始报 `false`——因为用业务池去查另一台实例的 `information_schema` 会静默得到 0 行，被误读成"账本表不存在"。现改为两侧各查自己的元数据。这类"不报错的错"正是信任模型页存在的意义。

## 三、意见② 关键数字无出处 + 摘要正文不一致

> **院审原文**：关键数字无出处（PoW 慢 79 倍、132 台设备）且摘要 894 笔与正文 895 笔不一致。
> **建议**：统一全部数字口径。

### 上一轮已做、本轮补强的部分

上一轮建了「指标溯源台账」（48 条，每条绑定产生命令 + 证据文件 + SHA-256）。本轮核查发现**台账机制对，但有漏洞**：

**漏洞 1：失败套件被标成 OK**

台账里 `verify.suites.failed` 的守卫只判断 `sumTotal` 是否非零。于是"1 套失败、断言 279/279 全过"这种状态被标成了绿色——这恰好是院审批评的"数字口径不统一"的同型问题：**汇总状态与明细状态不一致**。

已修：失败套件数 > 0 一律 SUSPECT，并列出是哪几套。

**漏洞 2：没有机器检查"同一数字在不同位置是否同值"**

台账回答"数字从哪来"，但没有回答"这个数全文是不是只有一个值"。新增 `tools/metrics-consistency.mjs`：

1. **汇总 vs 明细**：`verify-all` 的 `totals.*` 必须与 `rows[].status` 计数吻合；
2. **台账 vs 页面**：扫前端源码里指代全链/全网总量的表述（"全链共 N 笔""PoA 快 N 倍""接入 N 台设备"），与台账同值比对；
3. **同一概念多处不同值**：共识加速比在全文只允许一个值。

已接入 `npm run verify:all`（`consistency` 套件，排在 `ledger` 之后）。

**规则收紧过程（值得说明）**

第一版规则过宽，报出 10 处"错误"，但绝大多数是误报：

- `最近 50 笔` —— 是分页大小，不是全链总量；
- `1e12 倍` —— 科学计数法，正则把 `12` 抓了出来；
- `同行 2 倍`、`烟囱是标尺的 2.4 倍` —— 业务比较，与共识倍数无关；
- `1000 块 × 10 交易 = 10,000 笔` —— 合成基准规模。

把这些都算作口径矛盾，只会让真正的矛盾被淹没。现在只匹配**带全局限定词的句式**，并为每条规则写明"反例为什么被排除"。

同时删掉了页面上一句复述院审原话的文案（`院审：894/895 不一致、"79 倍""132 台"无出处`）——把有问题的数字留在产品界面上本身就不合适，改为不含数字的表述。

### 证据

```
台账 48 条  ✅ 48  🟡 0  🟠 0  🔴 0  ⛔ 0
口径 错误 0 · 告警 0 · 跳过 0
```

### 顺带修掉的一个真实缺陷（判据可证伪性）

回归时发现"验证总览"第⑤项**判据可证伪**显示 FAIL（3/4 类注入被检出）。追下去是真问题：

D 类注入"产品碳放大 10× 使其超过组织碳"，在试点期存证覆盖率仅 5% 的数据上**放大 10 倍仍然远小于组织碳**，包含性自然依然成立——这条"注入"其实什么都没注入。页面把它标成"漏检"，看起来像判据失效，实际是**测试用例设计和实际数据量级脱节**。

已改为先算"要超过组织碳至少需要放大多少倍"，再放大到它的 1.2 倍，并如实显示实际倍数：

```
D  产品碳放大 28×  邢台纸业：Σ产品碳 1263 → 35373 tCO₂e（×28）
   基线 pass=true，注入后 pass=false，不可解释量 10083.0 tCO₂e   已检出
```

修完后"六项主张"从 5/6 变为 **6/6 全部通过**。同时修掉了该用例 `entShort` 显示 `undefined` 的问题。

> 这一条值得单独说明：如果只是把 FAIL 改成 PASS，那是掩盖问题；真正的原因是注入强度没有随数据量级自适应，修的是用例而不是判据。

## 四、意见③ 实机测试系自举模拟、无真实企业数据

> **院审原文**：'实机测试'系自举模拟，无真实企业数据。
> **建议**：接入至少 1 家真实企业 CEMS 数据并请第三方复算。

### 这条为什么不能靠"写一段说明"解决

平台原有的数据分层做得其实不差：`truth_declaration` 表里已经明确写着"平台内 CEMS 读数由确定性模型生成"（MODELED），也有反向检查"不存在标记为真实但无数据源的记录"。问题不在叙述，而在**没有让真实数据进得来的通道**——没有通道，所谓"接入真实数据"就永远是一句计划。

### 整改：可执行的接入通道 + 第三方复算包

新增 `tools/real-cems-ingest.mjs`，支持三种输入：

| 模式 | 输入 | 适用场景 |
| --- | --- | --- |
| `--mode=hj212` | HJ 212-2017 原始报文 | 最接近真实数采仪 |
| `--mode=csv` | CSV（表头可带单位，如"排放速率(tCO2e/h)"） | 企业导出的历史数据 |
| `--mode=json` | JSON 行数组 | 企业已有 ETL |

**关键设计：不猜测、不补造**

- 报文缺 CRC 就标未校验，**平台不代算一个**；
- 时间不单调就**整批拒绝**——乱序通常意味着导出范围重叠或多排口混批，静默排序会掩盖问题；
- 企业未备案就拒绝入库——平台不会为接入数据而虚构一家企业；
- 批次号用内容寻址（`RCEMS-<sha256前24位>`），同一份报文重复导入天然幂等。

**第三方复算包**（`--recompute-package`）

产出 `tools/out/third-party-recompute.json`，只包含：

- 原始读数（时间、值、质量标记、设备 DID、CRC、SM3、序号）；
- 复算口径（"逐条求和 flow_value；若间隔 Δt 小时则排放量 ≈ Σ(flow × Δt)"）；
- 链上锚点（txId / payloadHash / 区块高度）；
- 边界说明（CRC 字段来自原始报文，平台未代为计算；采样间隔变化属真实数据正常形态）。

平台自己的算值单独放在 `expected` 里，并写明：

> **仅供比对：请先独立完成复算并写下你的结果，再对照本值**

若先看此值再算，复算就成了"凑答案"，失去独立验证的意义。

### 当前状态（如实）

```
真实接入批次      0 批     batch_no 以 RCEMS- 开头
真实读数          0 条
模拟读数     34,634 条     平台自举生成，非任何设备上报
第三方复算包   已生成
```

页面上直接显示这段提示：

> 当前**尚无真实企业 CEMS 数据接入**。平台不把模拟读数冒充实机测试：所有模拟读数在来源分层中计为 MODELED，对外表述必须同样标注。

`truth_declaration` 新增一条 `real_cems_batch_count`（期望 0，`AT_LEAST`）：事实变多不报错，事实变少立刻红。

### 必须说明的边界（不回避）

**真正的第三方复算还没有发生。** 通道、复算包、真实性声明都已就绪并验证可用，但:

1. 需要一家真实企业提供 CEMS 报文并授权使用；
2. 需要找到愿意出具复算结论的第三方机构。

这两件事都需要线下推进，不是本机可以替代的。因此本轮对这条意见的处置是：**把"没有真实数据"从"说不清"变成"说清楚且随时能接"**，而不是声称已经解决。

同样：EPA CAMD 逐小时 CEMS 接口需要专用 API Key（公开的前端 key 对该服务返回 `API_KEY_UNAUTHORIZED`），已核实无法直接取用。这一条也如实记录，不含糊过去。

## 五、意见④ "前后端分离"与"同端口单进程"矛盾

> **院审原文**：'前后端分离'与'同端口单进程'直接矛盾。

### 矛盾的成因

这两个词在描述**不同层面**，却被并列成了同一层面的两种说法：

- **应用形态**：单一 Node 进程同时提供 REST API 与前端静态资源——这就是同进程同端口，本地与线上一致；
- **资产托管**：线上把静态文件放 Cloudflare Pages、API 放 Workers/Render——这是托管产品的拆分。

更要紧的是：前端是**运行期编译的 Vue**（`vue.global.prod.js` + 原生 JS 视图），**没有独立构建产物、没有 Node 侧渲染**。因此"前后端分离架构"这个说法在本项目里根本不成立，不是"表述不一致"，是**说错了**。

### 整改

接口把三个维度分开返回，让人不可能再把它们混成一句话：

```json
{
  "runtime":      { "model": "single-process", "frontendBuild": "无独立构建产物…" },
  "assetHosting": { "separated": true, "statement": "线上托管分离…这是托管层的拆分" },
  "contract":     { "consistent": true },
  "oneLine": "单一 Node 进程提供全部 API 与静态资源；线上按托管产品拆成静态与 API 两个入口，共用同一套 API 契约。本平台不采用「前后端分离架构」这一说法。"
}
```

页面上按四维表格呈现（运行形态 / 前端构建 / 资产托管 / API 契约），并附一段"为什么会有过这个矛盾"的说明。全仓已无任何"前后端分离"的架构主张表述（包括构建产物 `dist/`）。

### 小程序（碳链通 · 掌上碳账本）

**链路页新增「信任模型」卡片**：隔离强度徽标（L3 / 已隔离）、业务库与账本库端点、业务库中的账本实体表数、篡改演练命中数、真实 CEMS 接入批次。

> 为什么手机端也要有：如果链库分离只在 Web 后台可见，它更像一个后台配置。放到公开可查的链路页上，任何人都能在手机上重跑一次核验。

**验真页新增「这次验证覆盖了什么」**：把三项已证明（区块头完整 / 交易集合完整 / 锚点与明文分离存放）和一项未覆盖（不校验业务数据本身的真实性）并排写出来。只说"可信"而不说边界，是评审最容易追问的地方。

同时修掉一个并发护栏缺陷：`onTrust` 原先用 `trustLoading` 做防重入，会让下拉刷新被上一次请求的 loading 状态误挡掉。改用独立的 `_trustBusy` 标志。
